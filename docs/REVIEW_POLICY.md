# PR·리뷰·머지 절차

> **문서 상태:** 현재 정본
> **권위 범위:** PR 발행부터 머지까지의 판정 규칙·정지 조건·게이트
> **후속 정본:** 없음
> **편집 정책:** 계속 갱신

이 문서는 **어느 클라이언트로 작업하든** 같게 적용된다. Claude Code 든 Codex 든, 사람이
직접 하든 마찬가지다. 그래서 규칙의 발동은 클라이언트 설정이 아니라 **GitHub 상태**에
걸려 있다 — 저장소가 소유할 수 없는 규칙은 저장소 규율이 아니다.

## 왜 이 문서가 생겼나

종전 절차는 「P3 이하만이면 즉시 머지 / P1·P2 가 하나라도 있으면 다음 라운드」였다. 그런데
**리뷰어는 P3 를 발급하지 않는다** — #422~#436 전 구간에서 P3 배지는 0건이었다. 종료 가지가
도달 불가능하니 재라운드 가지만 매번 발화했고, 실제 정지 조건은 규칙서가 아니라 「리뷰어가
침묵할 때」 하나로 퇴화했다.

그 결과가 2026-08-01 하루 실측에 그대로 남아 있다. #430 은 `+519/−12` 에 P1 이 한 건도
없었는데 **5라운드**를 돌았고(매 라운드 P2 1건), 마지막 지적은 `--budget-s inf` 를 argparse
가 받아준다는 입력 검증이었다. 반대로 P1 을 낀 #428·#436 은 각각 2라운드·30분 안에 끝났다.
**규모와도 심각도와도 무상관이었고, 오히려 역상관에 가까웠다.**

그래서 정지 조건을 **라운드 수에서 결함 집합으로** 옮긴다. 그리고 심각도 판정을 리뷰어의
배지에서 되찾아 온다 — 배지는 입력이지 분류가 아니다.

## 1. 트리아지 — 판정은 두 갈래뿐

리뷰 지적 하나마다 둘 중 하나로 **정산**한다. 정산하지 않은 지적이 하나라도 있으면 머지
게이트가 서지 않는다.

**차단(block)** — 다음 셋 중 하나라도 참이면. 이 PR 에서 고친다.

1. 오늘 사용자가 밟을 수 있다
2. 릴리스·영속·파괴 경로가 깨진다
3. 계약이 거짓말한다 — 표시·테스트·문서가 실제 상태와 다르다

**분리(defer)** — 그 외 전부. GitHub 이슈로 발행하고 번호를 남긴다.

「기각」이라는 판정은 없다. 오독이든 이미 가드된 것이든 **이슈로 남긴다**(라벨
`review-dismissed` + 사유 한 줄). 이유는 이 저장소의 원칙 그대로다 — 실패·거절은 숨기지
않고 사유를 재진술한다. 코멘트 한 줄로 지우면 나중에 그 판정이 틀렸을 때 되짚을 것이
없지만, 이슈로 남기면 복구할 수 있다. 그리고 이슈의 실재는 **기계로 확인된다**.

`master` 는 릴리스 경계가 아니다. 아직 도달 불가능한 표면의 잠재 결함은 심각해 보여도
차단이 아니라 분리다.

## 2. 정산 마커

정산은 지적 스레드 **안의 답글** 한 줄로 남긴다. `scripts/review_rounds.py` 가 파싱하는
계약이다.

```
triage: block:<1|2|3>
triage: defer #123
```

`block:` 뒤의 숫자는 §1 리트머스의 조항 번호다 — **어느 조항이 참인지 말하지 못하는 차단은
정의상 분리다.** 이 마찰이 「전부 차단」으로 쏠리는 손을 붙잡는다(#449 는 지적 15건 중
14건을 차단으로 정산했다 — 리트머스가 산문으로만 있으면 안 걸린다).

마커가 지적 스레드에 앵커되므로 코멘트 id 를 옮겨 적는 부기가 없고, 판정이 지적 **옆에**
남아 나중에 되짚을 때 문맥이 함께 보인다(검증된 봇 리뷰 도구들의 공통 형태다). 같은
스레드에 마커를 여러 번 남기면 **마지막 유효 마커가 이긴다** — 판정을 바꿀 때 앞 마커를
지우러 다니지 않는다.

**정산 의무는 리뷰어가 뿌리인 스레드에만 진다.** 작성자의 자기 메모·지나가는 코멘트는
정산 대상이 아니다 — 그 스레드의 해결은 룰셋의 「대화 해결 필수」(§7)가 따로 강제한다.

**신뢰의 축은 둘뿐이고, 밖에서 들어오는 모든 것이 그 둘 중 하나를 지난다.** 리뷰를 낸다고
인정하는 계정(리액션·인라인 지적)과, 정산을 남긴다고 인정하는 관계(`OWNER`·`MEMBER`·
`COLLABORATOR`)다. 원격 입력마다 따로 판정하면 한 군데를 조이는 동안 다른 데가 열린 채
남는다 — 실제로 리액션을 조인 라운드에 head 코멘트 경로가 그대로 열려 있었다.

`defer` 의 이슈 번호는 **실재하는지 API 로 확인한다** — 번호만 적어서는 통과하지 못한다.
이것이 「조용히 넘어감」을 막는 기계 장치다. 열려 있음까지는 묻지 않는다 — 분리한 이슈를
누가 먼저 고쳐 닫으면 아무것도 안 틀린 PR 이 빨간색이 되고, 이슈 상태 변화는 워크플로
이벤트를 만들지 않아 그 빨간색을 깨울 사건도 없다. 실재는 남는다 — 닫힌 이슈도 증거다.

두 가지가 더 기계로 강제된다.

- **`block` 은 그 리뷰 스레드를 `Resolve conversation` 해야 해소로 친다.** 마커만 달고
  넘어가면 게이트가 계속 빨간색이다.

  코멘트가 outdated 가 된 것은 **증거가 아니다.** 무관한 코드가 밀려 앵커가 사라져도
  outdated 가 되고, 반대로 정말 고쳐도 GitHub 이 최신 커밋으로 **재앵커**해 살아남는다 —
  어느 쪽으로도 틀린다. 해소의 증거는 「전부」이고 「의도적」이어야 한다. 스레드 해결은
  사람이 「이건 처리했다」고 남긴 원격 행위라 그쪽이 옳다.
- **마커가 아닌 답글은 그저 대화다.** 해명·질문이 정산 상태를 바꾸지 않고, 스스로 게이트를
  세우지도 않는다.

## 3. 정지 조건

**종료** = 미해결 차단 0건 **AND** 정산 완결 **AND** 이 PR 이 **한 번이라도 읽힘**
(리뷰어의 지적 또는 무결과 신호 수신, 혹은 회수 창 소진).

기본으로는 「마지막 push 를 봤는가」를 묻지 않는다. 자동 리뷰가 PR 당 한 번이므로 그렇게
늘 물으면 고칠 때마다 다시 안 읽힌 상태가 돼 영영 안 닫힌다. **단, 차단을 고쳤으면 그때는
묻는다** — 아래 「차단을 고쳤으면 반드시 다시 부른다」를 보라.

회수 창(10분)은 **정직한 1급 종료 조건**이다. 리뷰어의 「더 할 말 없음」 신호는 원리적으로
오지 않는다 — 이 리뷰어는 한 번에 한두 건씩 내는 증분 리뷰라 다시 부르면 늘 뭔가 더 나오고,
그래서 봇 리뷰 루프를 다루는 도구들이 공통으로 채택한 종결자가 **무활동 창**이다. 우리도
같은 것을 쓰되 숨기지 않는다: 창으로 닫힌 PR 은 체크런 제목에 「리뷰 없이 회수 창 소진」으로
**시끄럽게** 남는다. 조용히 초록이 되면 「리뷰를 받았다」와 「리뷰어가 침묵했다」가 같은
색이 된다. 그 표시를 보면 `@codex review` 로 한 번 명시 트리거해 보고, 그래도 무응답일 때
진행한다.

**단, 차단을 고친 PR 은 재리뷰를 부른 시점부터만 창이 돈다.** 부르지 않으면 창은 영영 돌지
않는다 — 종전에는 창이 push 부터 돌아, 안 불러도 10분 뒤 조용히 초록이 됐다. 그 길이 열려
있으면 「픽스가 읽힐 때까지 막는다」는 아래 문장이 거짓말이 된다.

**재리뷰 호출 예산은 2회다.** 세 번째 `@codex review` 를 부르기 전에 멈춘다 — 지적이 매번
달라도 같은 **결함류**일 수 있고, 그때는 점별 픽스가 아니라 류를 하나로 닫는 조치가 답이다
(파생 판정 단일화·가드 계약·타입 봉합). 이 신호는 게이트가 막아 주지 않는다. 실측이 이유다 —
이 규칙을 세운 PR 자신(#449)이 재호출 6회를 썼고, 그 폭의 절반은 고칠 것이 아니라 닫을
결함류였다. 라운드 수·회귀 후보를 기계로 세던 장치는 걷어냈다 — 자동 리뷰가 PR 당 한 번이면
라운드가 거의 안 생겨 그 계측은 도달 불가에 가깝고, 부기는 이 저장소에서 거듭 틀렸다(#450).

자동 리뷰는 **PR 당 한 번** 발화한다(2026-08-02 설정 변경). 종전에는 push 마다 발화했고,
그래서 **고치는 것이 push 를 만들고 push 가 리뷰를 불렀다** — 모든 지적을 차단으로 보고
고치면 종료 조건이 「리뷰어가 더 할 말이 없을 때」로 되돌아갔다. 이 문서가 폐기하려던 바로
그 상태다. 원인을 껐으므로 그 폭증을 유계로 만들려던 장치도 필요 없다.

**차단을 고쳤으면 반드시 다시 부른다.** 재리뷰는 저절로 오지 않는다.

```powershell
gh pr comment <PR> --body "@codex review"
```

고침은 새 코드이고 새 코드는 눈이 필요하다. 여기서 놓아 주면 라운드 폭증을 **미검토**로
맞바꾸는 셈이다 — 초기 diff 만 읽히고 그 뒤에 들어간 픽스는 영영 안 읽힌 채 머지된다.
게이트가 그것을 강제한다: 차단으로 정산한 것이 하나라도 있으면 **지금 head 가 리뷰어에게
읽히거나, push 뒤의 재호출이 회수 창을 소진할 때까지** 초록이 되지 않는다.

**차단이 지금 head 에 붙어 있으면 그 head 는 「픽스가 읽힌」 것으로 치지 않는다.** 그 지적은
바로 이 코드에 대한 것이니 고침이 아직 거기 없다. 이 단서가 없으면 head 에 받은 차단을
마커만 달고 스레드를 해결해 **픽스를 push 하지도 않고** 초록을 만들 수 있다.

**부르는 것은 push 뒤다.** 먼저 부르면 리뷰어가 옛 head 를 읽고, 정작 픽스는 안 읽힌 채
남는다. 순서가 계약이다.

**분리만 했다면 부르지 않는다.** 코드가 안 바뀌었으니 읽힐 것이 없고, 그래서 라운드가
옛날처럼 부풀지 않는다.

한 가지 거친 구석은 알고 쓴다: 차단을 고친 PR 에서 재리뷰까지 마친 뒤 리베이스나 문서
수정으로 head 를 **다시 움직이면**, 게이트가 그 head 를 안 읽힌 것으로 보고 **재호출을 한 번
더 요구한다**(재호출은 push 뒤라는 순서가 계약이라, 옛 재호출로는 새 head 의 창이 돌지
않는다). 「그 push 는 코드를 안 바꿨다」를 기계가 알게 하려면 경계를 저장해야 하는데, 그
부기는 이 저장소에서 세 라운드 연속으로 결함을 냈다(#450). 픽스 push 를 한 커밋으로 묶고
재호출 뒤에는 head 를 움직이지 않는 것이 싸다 — 그래서 순서가 절차에 있다.

루프가 안 닫히면 먼저 물을 것은 **「이걸 정말 이 PR 에서 고쳐야 하는가」**다. 분리는 마커와
이슈뿐이라 head 를 바꾸지 않으므로 그 자리에서 닫힌다.

## 4. 대기는 클라이언트 감시 루프가 하고, CI 는 강제한다

리뷰 도착을 기다리는 1차 주체는 **작업 중인 에이전트**다 — 봇 리뷰 루프를 다루는 검증된
도구들의 공통 형태(폴링 + 무활동 종료)를 그대로 쓴다. `/review-round` 의 감시 단계가 ~90초
간격으로 판정을 다시 읽고, 끝났으면 끝낸다.

한번 「CI 가 기다린다」로 뒤집었다가 되돌아왔다. CI 대기는 각성원이 필요하고, 그 각성원이
전부 못 미더웠다 — 리액션과 회수 창 경과는 워크플로 이벤트를 만들지 않고, cron 은 최선노력
큐라 실측으로 2.7시간 동안 0회 발화했다(2026-08-02). 그 형상에서 `WAIT` 인 PR 은 누가
코멘트를 달아 주기 전까지 **영영 재판정되지 않는다.**

`review-gate` 는 **대기가 아니라 강제**다. 리뷰·코멘트가 이벤트로 오면 그때그때 재판정해
체크런을 갱신하고, required check 로 머지를 막는다. 이벤트가 안 오는 축 — 리액션, 회수 창
경과, 그리고 **스레드 해결**(`pull_request_review_thread` 트리거는 Actions 파서가 거부한다,
2026-08-02 실측) — 의 재판정은 두 겹이다:

- **클라이언트 킥(1차)**: 감시 루프가 회수 창 경과를 보면
  `gh workflow run review-gate.yml -f pr=<PR>` 로 재판정을 깨운다. `workflow_dispatch` 는
  워크플로가 기본 브랜치에 있어야 동작한다. **머지 직전에도 같은 킥을 쓴다** — 로컬 판정을
  READY 로 넘긴 마지막 전이가 이벤트 없는 축이었다면 체크런은 낡은 색으로 남아 있고,
  required 체크가 걸린 뒤에는 그 낡음이 곧 머지 불능이다.
- **시간당 훑기(백스톱)**: cron 이 열린 PR 전부를 재판정한다. 킥마저 빠뜨린 PR 을 줍는
  안전망이지 엔진이 아니다.

이 루프에는 **입구**가 필요하다. 들어가는 것까지 절차의 판단으로 두면 PR 을 내고 다른 일로
넘어가는 길이 열린 채 남고, 그 PR 은 아무도 줍지 않는다 — 머지 게이트는 출구라 이 길을 영영
못 본다. 그 자리는 클라이언트 훅이 메운다(§7).

## 5. 빠른 경로

변경이 **산문 문서뿐**이면 `review-gate` 가 리뷰 회수를 기다리지 않고 즉시 초록이 된다.
선언도 마커도 필요 없다 — diff 자체가 증거다.

- 최상위 `*.md`(`README.md` 등), 또는 `docs/` 아래의 `.md`·`.html`
- 단 `docs/UI_CONTRACT.md` 는 제외한다 — 계약 원문이다
- **규칙서 자신도 제외한다** — `docs/REVIEW_POLICY.md`·`CLAUDE.md`·`AGENTS.md`. 규칙서가
  빠른 경로면 리뷰 규칙을 무리뷰로 고칠 수 있다. 규칙서는 규칙의 대상이다.

**허용 목록이지 금지 목록이 아니다.** 금지 목록으로 짜면 새로 생긴 경로가 기본값으로
통과한다. 그래서 `docs/` 아래여도 기계가 읽는 `package_coverage_floors.toml` 같은 파일은
확장자에서 이미 걸린다.

`tests/`·`scripts/` 는 **빠른 경로가 아니다.** 그 둘은 게이트 기계이고, 게이트가 깨지면
계약이 거짓말한다(§1 리트머스 3번). 101 하니스는 몇 달째 깨진 채였는데 어떤 게이트도 그것을
보지 못했고(#423), PR #426 은 `scripts/`·`tests/` 만 고치고도 P1 을 2건 받았다.

머지 뒤에 도착한 지적은 버리지 않고 **스윕 PR** 로 회수한다. 이 회수를 건너뛰어 미조치
P1 7건·P2 9건이 쌓인 적이 있다(PR #234~#279 → #280 에서 일괄 수습).

## 6. 머지·스택 규약

- **squash 머지.** 커밋 메시지는 한국어 Conventional Commits + `(이슈) (PR)`.
- 스택 PR 착지: 아래부터 squash → 다음 PR 을 `--base master` 로 리타깃 → 그 브랜치를 master
  위에 **자기 커밋만 cherry-pick 으로 재적용** → 그 브랜치에서 게이트 → 푸시 → 다음.
  `git rebase master` 는 이미 머지된 아래 PR 의 커밋을 replay 해 충돌만 만든다.
- **tip 만 초록인 것은 스택이 초록인 것이 아니다.** 파일을 위 브랜치에서 끌어오면 아래 PR
  이 구현 없이 위 PR 의 테스트를 갖는다. 브랜치마다 그 브랜치 게이트를 돌린다.
- PR 번호를 발행 전에 미리 적지 않는다 — 그 번호가 나중에 남에게 발급된다.

## 7. 게이트와 그 한계

| 층 | 실물 | 우회 가능성 |
|---|---|---|
| 룰셋(코드 0줄) | PR 필수 · **대화 해결 필수** · squash 한정 · 삭제/강제 push 금지 | 없음 — GitHub 이 강제 |
| 필수 체크 | `quality-gate`(품질) · `review-gate`(이 문서) | 없음 — ruleset 이 강제 |
| 판정기 | `scripts/review_rounds.py` | — 판정 로직의 단일 출처 |
| 클라이언트 훅 | `.claude/settings.json` 의 `PostToolUse`·`Stop`·`PreToolUse` | 있음 — 그 클라이언트에서만 뜬다 |

**룰셋이 맨 위인 이유**: 스레드 해소의 강제는 GitHub 네이티브 기능(「대화 해결 필수」)이
공짜로 해 준다 — 우리 판정기가 그 위에 얹는 고유분은 **정산 마커의 실재·문법, defer 이슈의
실재, 리뷰 1회 회수, 픽스 재읽힘**뿐이다. 존재하는 기능으로 지킬 수 있는 것을 코드로 다시
짓지 않는다. 룰셋의 실물은 §10 런북이 세운다.

**훅은 게이트가 아니다.** 웹 UI 머지도, 다른 에이전트도, 터미널에서 직접 친 `gh` 도 못
막는다. 훅은 CI 왕복 전에 낭비를 줄이는 빠른 실패일 뿐이고, 머지를 실제로 막는 것은
required check 다. 셋 다 같은 스크립트를 부르므로 판정이 여러 곳에 있지는 않다.

훅 셋이 맡는 것은 게이트가 아니라 **입구와 출구**다.

- `PostToolUse` — `gh pr create` 의 **결과**에서 저장소와 PR 번호를 집어 감시 목록에 올리고 그
  사실을 세션에 알린다. 막지 않는다. 명령만 보고 올리면 실패한 발행까지 감시하게 된다.
- `Stop` — 감시 목록이 비어 있지 않으면 턴이 끝나기 전에 판정을 읽고, `READY` 가 아니면
  **종료를 붙잡는다**. 대기(`WAIT`)도 붙잡는다 — 발행 직후의 대기가 곧 루프가 끊기는 지점이라
  거기서 놓아 주면 겨눈 것을 그대로 놓친다.
- `PreToolUse` — 머지 직전의 빠른 실패.

감시 목록은 `.git/` 안에 산다(커밋될 수 없고, 무시 규칙을 새로 더할 필요도 없다). **공용**
git dir 을 쓰는 이유는 worktree 다 — lane 이 worktree 에서 PR 을 내고 오케스트레이터가 본체에서
턴을 끝내면, 목록이 따로 살 때 그 PR 을 아무도 못 본다. 그 안은 **PR 당 파일 하나**다. 목록
하나를 읽고-고쳐-쓰면 두 lane 이 같은 순간에 발행할 때 나중 쓰기가 앞 PR 을 삼키고, 그러면
병렬 웨이브에서 감시가 조용히 빈다 — 공용 dir 로 옮긴 이유가 바로 그 시나리오였다.

**한 세션에게 같은 판정은 한 번만 말한다.** 붙잡기의 목적은 인지이고, 이미 감시에 들어간
세션에게 같은 말을 되풀이하는 것은 인지가 아니라 잔소리다 — 훅은 그 둘을 구분하지 못한다.
판정이 달라지면(지적 도착, 차단 해소, 재호출 필요) 다시 붙잡는다. 붙잡기는 상태를 바꾸지
못하므로 같은 판정에서 두 번 붙잡는 길이 없고, **무한 루프 방지가 임의의 예산이 아니라 구조에서
나온다.**

**확인은 세션 단위다.** 「들었다」는 그 세션의 대화가 갖는 성질이지 PR 이 갖는 성질이 아니다 —
PR 단위로 적어 두면 lane 세션이 들은 것을 오케스트레이터가 들은 것으로 치고, 아무도 못 들은 채
본체 턴이 끝난다(공용 dir 로 옮긴 목적 그 자체가 무너지는 자리다). 그래서 확인은 세션마다 자기
파일에 적힌다. **세션을 모르면 붙잡는 쪽으로 틀린다.**

상태를 **못 읽을 때는 붙잡지 않는다**: 인증 하나 끊긴 것이 세션을 벽돌로 만들면 안 되고, 그
경우에도 머지는 못 한다.

### 정체성을 값으로 대체하지 않는다

이 층을 짓는 동안 같은 결함이 네 번 났다 — 저장소를 버려 **다른 PR 이** 같아 보였고, 파일
이름의 `/`→`-` 치환이 **다른 저장소를**, 카운트 지문이 **다른 지적 집합을**, PR 단위 확인이
**다른 세션을** 같아 보이게 했다. 넷 다 정체성을 손실 압축한 파생을 정체성 대신 쓴 것이고,
결과는 매번 같다: **서로 다른 것이 같아 보이면 하나가 조용히 사라진다.**

그래서 규칙을 하나로 못박는다. **파생 표현은 정체성을 잃지 않게 담거나 아예 쓰지 않는다.**

- PR 의 자리는 `<owner>/<repo>/<pr>/` 중첩이다. GitHub 이름에 `/` 가 못 들어가므로 두 튜플이
  같은 경로로 갈 수 없다. 그 전제를 지키려고 이름 문자를 쓰기 직전에 다시 검사한다(`..` 같은
  조각이 감시 폴더 밖을 겨누는 것도 여기서 막힌다).
- 확인은 그 아래 **세션마다 자기 파일**이다. 파일 이름은 세션 id 의 해시다 — 되읽을 일이 없고
  필요한 것은 같음 판정뿐이라 충돌 저항으로 충분하고, 경로에 못 쓸 문자가 섞이는 길도 닫힌다.
- 지문은 **지적을 세지 않고 지목한다.** 하나가 정산되는 사이 하나가 도착하면 수는 그대로이고,
  그러면 새 지적이 「이미 말한 것」으로 삼켜진 채 턴이 끝난다. 지적 집합이 비어도 참이 되는
  「재호출 필요」도 지문에 든다 — 차단을 고치고 해결한 직후가 그 모양이고, 그때 새로 생기는
  지시가 발행 직후의 침묵과 같은 값이 되면 삼켜진다.
- 렌더 전체를 지문으로 쓰지는 않는다. head 는 push 마다 움직이는데 그때 할 말이 새로 생기는
  것은 아니라서, 작업 중인 세션을 push 마다 붙잡게 된다.

읽고-고쳐-쓰기가 어디에도 없다는 점이 이 배치의 핵심이다. 각 파일에는 **쓰는 주체가 하나뿐**이라
(그 PR 을 낸 쪽 / 그 세션) 잠금 없이도 서로를 지울 수 없다.

**훅으로 스킬을 자동 호출할 수는 없다.** 클라이언트 계약상 훅은 도구·스킬을 대신 부르지 못하고
막거나 컨텍스트를 심는 것만 한다. 그래서 이 셋이 만드는 것은 「자동 발동」이 아니라 **모르고
지나가는 길의 부재**다. 그 구분이 이 층을 하한으로 붙잡아 둔다.

`review-gate` 는 `pull_request` 가 아니라 `pull_request_target` 으로 돈다. 전자는 PR 판본의
워크플로와 스크립트가 도는데, 그러면 **PR 이 자기 게이트를 약화시킬 수 있다.**

## 8. 판독 노하우

리뷰 상태를 API 로 읽을 때 잘못 세기 쉬운 지점들이다. `review_rounds.py` 가 이대로
구현돼 있다.

- **코멘트의 `commit_id` 는 못 믿는다.** GitHub 은 앵커 hunk 가 살아 있는 한 코멘트를 최신
  커밋으로 **재앵커**한다 — 고쳐도 살아남고, 무관한 코드가 밀려도 outdated 가 된다. 지적이
  어느 코드를 겨눴는지는 `original_commit_id` 가 담고, 해소의 증거는 스레드 해결뿐이다.
- **무결과는 코멘트가 아니라 리액션으로 온다.** 지적이 없으면 리뷰어는 PR 에 `+1` 만 남긴다.
  `eyes` 는 진행 중이라는 뜻이다 — 둘을 혼동하면 리뷰를 안 기다리고 넘어간다.
- **회수 창은 10분이다.** 그 안에 아무 신호도 없으면 회수 창 소진으로 본다.
- 폴링이 헛돈다고 판단되면 `@codex review` 코멘트로 명시 트리거를 건다.

## 9. 도구

```powershell
uv run python scripts/review_rounds.py            # 현재 브랜치 PR 의 상태 표
uv run python scripts/review_rounds.py 430 --json # 특정 PR, 기계 판독용
```

CI 는 같은 스크립트를 `--publish-check` 로 불러 판정을 **PR head SHA 의 `review-gate`
체크런**으로 게시한다. 이벤트에 따라 워크플로의 기본 status 가 기본 브랜치에 붙어 버리기
때문에, 체크런을 직접 게시하는 경로 하나만 쓴다.

판정과 exit code:

| 판정 | exit | 뜻 |
|---|---|---|
| `READY` | 0 | 머지해도 된다 |
| `WAIT` | 1 | 리뷰 미회수(창 안) 또는 미정산 지적 존재 |
| `BLOCKED` | 1 | 미해결 차단 존재, 또는 분리 이슈가 실재하지 않음 |
| — | 2 | 조회 실패·미인증. **조용히 통과시키지 않는다** |

스크립트는 「이것이 차단인가」를 스스로 판단하지 않는다. 그 판정은 §1 리트머스로 사람·
에이전트가 하고 §2 마커가 담는다. 스크립트가 세는 것은 **정산의 완결성**이다 — 판정과
계측을 섞지 않는다.

Claude Code 에서는 `/review-round` 가 이 절차를 순서대로 돈다.

## 10. 룰셋 런북

룰셋은 API 상태라 git 이 못 지킨다 — 그래서 세우는 명령·확인하는 명령·끄는 명령을 여기
적는다. 드리프트 검증은 pytest 가 아니라 이 런북이다(네트워크·토큰이 필요해 결정론 contract
suite 에 못 들어간다).

**Step A — 머지 규율(체크 의존 없음, 재설계 착지 직후):**

PowerShell here-string 을 표준 입력으로 흘린다 — Bash heredoc(`<<'JSON'`)은 이 저장소의
문서화된 셸(PowerShell)에서 파싱조차 안 된다.

```powershell
@'
{ "name": "merge-discipline", "target": "branch", "enforcement": "active",
  "conditions": { "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] } },
  "rules": [
    { "type": "deletion" },
    { "type": "non_fast_forward" },
    { "type": "pull_request", "parameters": {
        "required_approving_review_count": 0,
        "dismiss_stale_reviews_on_push": false,
        "require_code_owner_review": false,
        "require_last_push_approval": false,
        "required_review_thread_resolution": true,
        "allowed_merge_methods": ["squash"] } }
  ] }
'@ | gh api repos/rfastball/hwpx-filler/rulesets -X POST --input -
```

**Step B — required checks 승격(`review-gate` 가 실 PR 에서 초록을 한 번 낸 뒤에만):**

```powershell
# context 문자열은 추측하지 않는다 — 실제 체크런 이름을 먼저 확인한다
gh api "repos/rfastball/hwpx-filler/commits/<sha>/check-runs" --jq '.check_runs[].name'

# 룰셋을 통째로 다시 보낸다(Step A 의 rules 배열에 아래 항목을 추가한 형태)
#  { "type": "required_status_checks", "parameters": {
#      "strict_required_status_checks_policy": false,
#      "required_status_checks": [
#        { "context": "review-gate" }, { "context": "quality-gate" } ] } }
gh api repos/rfastball/hwpx-filler/rulesets/<id> -X PUT --input ruleset.json
```

**순서가 계약이다.** 존재하지 않는 required check 를 먼저 걸면 **모든 PR 이 영구 대기**한다.

**드리프트 확인** (룰이 실제로 걸려 있는가):

```powershell
gh api repos/rfastball/hwpx-filler/rules/branches/master --jq '[.[].type] | sort'
# 기대: ["deletion","non_fast_forward","pull_request","required_status_checks"]
```

**비상 탈출** (룰셋이 master 를 벽돌로 만들었을 때 — bypass actor 를 두지 않았으므로 이
명령이 유일한 문이다):

```powershell
gh api repos/rfastball/hwpx-filler/rulesets/<id> -X PUT -f enforcement=disabled
```
