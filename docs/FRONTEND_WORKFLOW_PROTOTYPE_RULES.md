# 프론트엔드 워크플로 시안 작성 원칙

> **문서 상태:** 현재 정본
> **권위 범위:** 이 워크트리의 HTML 기반 인터랙티브 시안과 후속 프론트엔드 화면
> **편집 정책:** 워크플로 원칙이 변경될 때만 갱신

## 목적

프론트엔드 시안은 백엔드 기능 목록을 보기 좋게 배치하는 화면이 아니다. 기존 백엔드의 원자
동작을 사용자의 실제 작업 순서에 맞게 재구성하고, 단계·조건·실패·복구를 명시적인 워크플로
계약으로 표현해야 한다.

기존 시안은 처음부터 다시 만들지 않는다. 조사 → 감사 → 유지/수정/재설계 분류 → 직접 교정 →
재검증 순서로 작업한다.

## 1. 워크플로가 기준이다

모든 주요 단계는 다음 질문에 답해야 한다.

- 사용자는 지금 어느 단계에 있는가?
- 진입 조건과 완료 조건은 무엇인가?
- 지금 가장 먼저 해야 할 하나의 주 행동은 무엇인가?
- 다음 단계와 이전 단계는 무엇인가?
- 돌아갈 때 어떤 입력과 결과가 보존되는가?
- 실패하면 어디에 머물고 무엇을 재시도하는가?
- 지금 불가능한 행동과 그 이유·해결 방법은 무엇인가?

답하지 못하는 화면이나 버튼은 역할을 다시 정의한다. 하나의 단계에 같은 강조도의 주 행동을
여러 개 두지 않는다. 고급·예외·위험 행동은 기본 진행 흐름보다 낮은 위계로 분리한다.

## 2. 백엔드 원자 동작을 그대로 노출하지 않는다

백엔드 함수·명령·API 하나마다 버튼을 만들지 않는다. 생성, 갱신, 검증, revision 생성, 상태 변경
같은 내부 동작은 다음과 같은 완결된 사용자 행동으로 묶는다.

- 새 문서 시작
- 작성 내용 저장
- 결과 검토
- 문서 생성
- 작업 확정
- 실패 항목 다시 실행
- 이전 단계로 돌아가기

사용자 행동 하나가 여러 백엔드 원자 동작의 조합이어도 된다. 이 경우 capability를 `composed`로
기록하고 실제 구현에서 필요한 operation 경계를 남긴다.

## 3. 워크플로 계약을 중앙에서 관리한다

화면 전이와 조건을 클릭 이벤트에 흩어 놓지 않는다. 현재 기술 수준에 맞는 중앙 정의에서 최소한
다음을 확인할 수 있어야 한다.

- 단계 ID와 사용자 표시 이름
- 진입 조건과 완료 조건
- 주 행동
- 다음·이전 단계
- 실패 상태
- 단계별 사용 가능 행동
- 단계별 제한 사항

라우팅 함수와 화면 이벤트는 이 계약을 통과해야 한다. 화면을 열었다는 사실만으로 단계 완료,
저장, 승인 또는 확정으로 처리하지 않는다.

## 4. 상태 축을 분리한다

하나의 `currentStep`이나 화면 ID에 모든 의미를 넣지 않는다. 최소한 다음을 독립적으로 관리한다.

- 현재 보고 있는 화면
- 실제 워크플로 단계
- 백엔드 요청·처리 상태
- 사용자 입력 상태
- 저장 상태
- 검증 상태
- 오류 상태
- 미리보기 생성 상태와 승인 상태
- 처리 결과와 확정 상태

설정 화면에서 다른 문서를 조회하는 일과 실제 실행 문서를 바꾸는 일처럼 의미가 다른 사건도
별도 상태와 명시적 행동으로 구분한다.

## 5. capability를 명시한다

모든 주요 행동은 다음 중 하나로 분류한다.

| 상태 | 의미 |
|---|---|
| `supported` | 기존 동작으로 현재 구현 가능 |
| `composed` | 여러 기존 동작을 조합하면 구현 가능 |
| `unsupported` | 현재 구조에서는 구현 불가능 |
| `deferred` | 가능성은 있으나 현재 범위에서 연기 |
| `removed` | 기존에 있었으나 새 워크플로에서는 폐기 |

지원되지 않는 기능을 성공한 것처럼 흉내 내지 않는다. 제품 범위에서 빠졌다면 제거하고, 제약
이해에 필요하면 이유와 해결 방향을 설명한다. 시안 검토를 위해 위치만 유지한다면 시안 전용임을
명시한다. 이유 없는 비활성 버튼을 쌓아 두지 않는다.

## 6. 정상 경로 외 상태를 구현한다

핵심 워크플로에는 필요한 범위에서 다음 상태를 표현한다.

- 초기·빈 상태
- 입력 중·변경 사항 있음
- 검증 대기·검증 실패
- 실행 대기·처리 중
- 성공·부분 성공·실패
- 재시도·취소 요청·취소 완료
- 저장 중·저장 완료·저장 실패
- 이전 단계 복귀
- 완료·확정

백엔드가 연결되지 않았다면 명시적인 prototype outcome으로 전환할 수 있게 한다. mock은 실제
성공처럼 위장하지 않고 시안 상태 전환임을 보여준다.

## 7. 실패와 비동기 규칙

- 실패해도 입력값과 선택을 초기화하지 않는다.
- 재시도 범위와 다시 실행되는 동작을 설명한다.
- 이전 성공 결과는 새 실패로 지우지 않는다.
- 사용자 작업이 손실될 수 있는 이동에는 보존 방식이나 확인 절차를 둔다.
- 오류 코드만 노출하지 않고 다음 행동을 함께 제시한다.
- 요청 전, 요청 중, 완료, 실패, 재시도 중, 취소 요청 중을 구분한다.
- 처리 중 중복 클릭과 중복 요청을 막는다.
- 부분 성공을 전체 성공으로 표시하지 않는다.

미리보기 생성과 사용자의 결과 승인은 서로 다른 사건이다. drawer·modal을 열거나 결과가
렌더됐다는 이유로 자동 승인하지 않는다.

## 8. 코드 경계

다음 역할을 구분한다.

- UI 마크업과 렌더링
- 워크플로 계약
- 런타임 상태 저장
- 사용자 행동 처리
- mock 백엔드
- capability 정의
- 샘플 데이터

작은 시안은 파일을 지나치게 쪼개지 않아도 되지만 역할 경계는 분명해야 한다. UI 이벤트가 mock
함수를 곳곳에서 직접 호출하지 않게 하고, 한 경계에서 실제 워크플로 구현체로 교체할 수 있어야
한다. 거대한 범용 어댑터나 프레임워크는 만들지 않는다.

컴포넌트·화면·버튼 이름은 사용자 작업과 의미를 기준으로 한다. 백엔드 API 이름이 사용자 언어를
지배하게 하지 않는다.

## 9. UI·문안·접근성

- 현재 단계, 완료된 단계, 남은 단계, 복귀 가능한 단계와 지금 필요한 일을 보여준다.
- 내부 상태명·데이터 모델명·오류 코드를 사용자 언어로 번역한다.
- 같은 의미의 행동은 같은 이름을 사용한다.
- `저장`, `생성`, `확정`, `내보내기`, `복사`의 의미를 섞지 않는다.
- 상세·고급·드문 기능은 필요한 시점에만 노출한다.
- 클릭 요소는 `button`, `a`, `input` 등 의미 요소를 사용한다.
- 입력에는 명시적인 label을 연결한다.
- 색만으로 상태를 구분하지 않는다.
- 포커스 표시를 유지한다.
- modal·drawer를 열고 닫을 때 포커스 이동·배경 격리·호출점 복귀를 처리한다.
- 오류 메시지를 관련 입력과 연결한다.
- 처리 중 상태를 텍스트와 `aria-live` 등으로 전달한다.
- 아이콘 전용 버튼에는 접근 가능한 이름을 제공한다.

사용자 가시 용어는 `docs/UI_VOCABULARY.md`를 우선한다.

## 10. 감사와 교정 절차

수정 전에 관련 파일과 현재 동작을 조사한다.

- 화면과 주요 컴포넌트
- 화면 전환 방식
- 상태 저장 방식
- 주요 버튼과 행동
- mock 데이터와 mock API
- 백엔드 capability
- 숨겨진·미완성 화면
- 빈·로딩·실패 상태
- 워크플로 시작점과 종료점
- 중복·모순 행동
- 직접 노출된 백엔드 원자 동작
- 흩어진 전이 조건

감사 결과는 다음으로 분류한다.

- `유지`: 현재 원칙을 잘 지켜 보존할 부분
- `수정`: 기존 구조를 유지하며 바로잡을 부분
- `재설계`: 워크플로를 방해해 구조 변경이 필요한 부분

각 위반에는 위치, 현재 상태, 위반 원칙, 사용자 영향, 수정 방향, 수정 범위를 기록한다. 추상적인
“UX가 나쁘다” 대신 실제 파일·화면·컴포넌트와 전이를 근거로 든다.

## 11. 교정 우선순위

1. 워크플로 순서 불명확
2. 지원되지 않는 기능의 거짓 약속
3. 백엔드 원자 동작의 직접 노출
4. 주 행동 충돌
5. 성공 경로 외 상태 부재
6. 입력·결과 손실
7. 흩어진 전환 조건
8. 용어·행동 이름 불일치
9. mock/UI 과결합
10. 접근성·HTML 의미 구조

확인되지 않은 기능을 임의로 추가하지 않는다. 기존 동작 조합이면 `composed`, 현재 불가능하면
`unsupported`, 범위 미확정이면 `deferred`, 불필요하면 `removed`로 기록한다.

전면 재작성은 현재 구조로 워크플로를 표현할 수 없고 국소 수정이 더 복잡하며 보존 가치가 없을
때만 선택한다.

## 12. 수정 후 필수 검증

### 워크플로

- 시작과 종료가 명확한가?
- 단계 순서·조건·복귀·실패가 중앙 계약에 있는가?
- 실패 후 입력과 결과가 보존되는가?
- 각 단계의 주 행동이 하나인가?

### capability

- 주요 행동의 지원 상태와 근거가 있는가?
- 미지원·폐기 기능이 활성화되어 있지 않은가?
- `composed` 행동의 조합 operation이 기록되어 있는가?

### 상태

- 빈·대기·처리·실패·재시도·저장·부분 완료 상태가 필요한 곳에 있는가?
- 화면 위치와 실제 작업 상태가 섞이지 않았는가?

### 구조

- 전환 조건이 이벤트 핸들러에 흩어지지 않았는가?
- mock과 UI가 분리되어 있는가?
- 실제 백엔드 연결 지점을 교체할 수 있는가?
- 불필요한 범용 추상화가 없는가?

### UI

- 현재 위치와 다음 행동을 쉽게 이해할 수 있는가?
- 용어가 일관적인가?
- 고급 기능이 기본 흐름을 가리지 않는가?
- 제한 행동에 이유와 해결 방향이 있는가?
- 키보드·의미 HTML·포커스 계약을 지키는가?

정적 계약 검사와 실제 브라우저 핵심 흐름을 모두 실행한다. 구조 검사만으로 클릭·포커스·비동기
전이를 대신하지 않는다.

## 13. 결과 보고

작업 결과는 다음 순서로 기록한다.

1. 현재 상태 요약
2. `항목 | 상태 | 근거 | 조치` 감사표
3. 수정한 파일·워크플로·상태·계약·접근성·mock
4. 직접 확정할 수 없는 남은 항목과 capability 상태
5. 핵심 원칙별 `통과`, `조건부 통과`, `미통과` 재검증 결과

수정 가능한 `미통과` 항목을 남겨 둔 채 완료로 보고하지 않는다.
