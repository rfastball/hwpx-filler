# U2 실사용 피드백 라운드 — 트리아지와 판정

> **문서 상태:** 유효 결정 (진행 중 — 미결 항목 보유)
> **권위 범위:** v6 표면 착지 이후 받은 실사용 피드백의 분류·판정·미결 목록
> **후속 정본:** 없음
> **편집 정책:** 항목이 닫힐 때마다 판정을 추가하고, **코드에 닿은 항목은 이름에 취소선 +
> 「조치완료(#PR · 커밋)」을 병기한다**. 이슈의 열림/닫힘 상태는 GitHub 이 소유한다.
> **취소선 단독은 뜻이 없다** — 뒤에 오는 굵은 표식(`조치완료` / `판정 이동 → §x.y` /
> `폐기`)이 뜻을 준다. **`폐기` 는 「안 하기로 했다」가 아니라 「다른 판정이 원인을 없애
> 지을 것이 남지 않았다」** 이고, 그 경우 **조치 표를 지운다** — 남겨 두면 다음 사람이 구현한다

v6 표면 전면 재작성(R1·F1~F8)이 완주한 직후 받은 **실사용자 피드백 34건**. 이전 U-라운드
(2026-07-23)는 재작성 **이전** 표면의 것이므로, 이번이 새 2탭 셸·라이브러리·드로어·작업대
형상에 대한 **첫 외부 실측**이다. 전 항목을 코드에 대조한 뒤 3분류했다.

**원문 전문 재대조(2026-07-29)** — 트리아지가 원문을 줄여 옮기면서 제안의 절반이나 기준면이
빠진 3건(§2.2 정렬 기준면 · §2.4 저장 버튼 라벨 · §5.2 종료 가드 우선순위)을 되돌렸다.
이 문서와 원문이 갈리면 **원문이 이긴다** — 여기 적힌 것은 원문의 요약이 아니라 그 위의
판정이므로, 요약 과정에서 사라진 조건은 판정의 근거까지 바꾼다.

재작성 자체의 근거 원장은 동결됐다 —
[`docs/archive/DATA_FIRST_INTEGRATION_MAP.md`](archive/DATA_FIRST_INTEGRATION_MAP.md).

### ~~2.1 `.zone` CSS 유실 회귀 (P1, 단일 근본원인)~~ — **조치완료**(#330 · `05c0c69`)

> **귀인 정정(2026-07-29, 착수 실측).** 이 절은 처음에 *"9분할에서 이관 없이 소멸"* 이라고
> 적었다. git 실측은 다르다 — 기제가 **분할이 아니라 과다 삭제**다. 분류·조치는 그대로지만
> 후속 규칙이 달라지므로(아래) 근거를 고쳐 적는다.
>
> | 사실 | 증거 |
> |---|---|
> | `67894b0` 시점엔 아직 `app.css` 단일 파일이었다 | `git show 67894b0:web/css/job.css` → `fatal: ... exists on disk, but not in '67894b0'` |
> | 9분할은 **그 뒤** 별도 커밋이고 바이트 보존이었다 | `6b9a98e`(#322) |
> | 규칙은 `67894b0`(F6 PR-B, #317 「기안」 사망)에서 `.draft-duo` 를 지우는 **같은 hunk** 에 `-` 로 딸려나갔다 | `git show 67894b0 -- web/css/app.css` |

`67894b0`(F6 PR-B, #317)이 「기안」 화면을 죽이며 `.draft-duo` 계열을 지울 때 아래 규칙군이
**곁달려 함께** 삭제됐다. `.draft-duo` 는 화면과 함께 죽는 것이 맞았지만 이 넷은 살아 있는
「문서 만들기」가 쓰던 것이다. **착수 당시**(#330 복구 이전) `web/css/` 전체에 `.zone` 규칙이
0개인데 `web/css/job.css:217-224` 주석은 아직 그 규칙을 설명했다 — **주석만 살아남았다.**
(시점을 박아 둔다. 안 박으면 다음 사람이 이 문장을 지금의 실측으로 읽고 회귀를 다시 센다.)

```css
/* git show 67894b0~1:web/css/app.css:894-898 */
.job-zones{display:flex;flex-direction:column; ...}
.zone{padding:var(--sp-16) var(--sp-16) var(--sp-12);position:relative}
.zone + .zone{border-top:1px solid var(--a-border)}
.zone-cap{display:block;margin-bottom:var(--sp-10); ...}
```

| 피드백 | 이 회귀가 내는 증상 |
|---|---|
| 좌우 열 간격이 좁다 | 존 패딩 0 + `.data-grid` gap 미선언 → 콘텐츠가 `border-left` 1px에 맞붙음 |
| 섹션별 식별성 부족 | 인접 존 구분선 소멸 |
| 캡션이 눈에 안 들어온다 | `.zone-cap{display:block}` 소멸로 인라인 흐름에 섞임 |

**조치**: 규칙군을 `web/css/job.css`(존 소유자)로 복구. `draft-duo`·`.zone.workcard` 관련
규칙은 `draft` 화면 사망(F6 PR-B)과 함께 무효이므로 되살리지 않는다.

**`.data-grid` 열 간격은 명시하지 않는다**(착수 실측으로 뒤집힌 조치). 위 표의 「좌우 열
간격이 좁다」는 gap 미선언이 아니라 **존 패딩 0** 이 원인이다 — `.zone{padding:16px}` 이
돌아오면 두 열의 존이 각자 16px 를 갖고 구분선 양쪽에 서므로 해소된다. 원인이 하나인데
조치를 둘 넣으면 다음 사람이 어느 쪽이 일한 것인지 못 센다.

**반대 방향으로 남은 죽은 CSS 2건**(규칙은 있는데 생산자가 없다 — 위 그물이 안 잡는 축):

- `job.css:150-158` `.job-master`·`.master-splitter` — 좌 master 목록 사망(F2 PR-B)으로
  대응 DOM이 없다
- `job.css:178-196` `.job-row`·`.job-more`·`.job-grp` — 같은 사망의 유산인데 **지금은
  편집기 템플릿 탭(`.libselrow .job-more`)이 그 규칙을 먹고 산다**. 죽은 화면의 CSS 파일이
  산 화면을 부양하는 상태

**같은 커밋이 주석을 고쳐 썼다** — 이 사고에서 제일 나쁜 부분이다:

```diff
- ... zone-cap 은 절대 legend 대신 인라인 섹션 헤더. job·draft 공통(둘 다 .zone). */
+ ... zone-cap 은 절대 legend 대신 인라인 섹션 헤더. job 소유(.zone). */
```

규칙을 지운 손이 *"이제 job 이 `.zone` 을 소유한다"* 고 적어 뒀다. 소유자를 명시했으니
남은 사람은 규칙이 있다고 읽는다 — **흔적으로도 못 잡는다.**

**후속 규칙 — 「삭제는 의무를 상속한다」의 공유-표면판.** 표면을 죽일 때 위험한 것은 그
표면의 규칙이 아니라 **그 표면과 이웃이 나눠 쓰던 규칙**이다. 죽는 쪽만 보고 지우면 산 쪽이
말없이 벗겨진다. 이슈 **#325**(CSS 소유권 재정렬 — 선행 = 시각 회귀 그물)가 이 사고를
예언했고, 그물이 없어 **세 슬라이스**를 통과했다(사망 → 분할 → 착지).

그래서 복구와 **같은 PR** 에 그물을 붙인다 — `tests/test_web_css_orphan_classes.py`:
DOM 이 내는 class 중 CSS 규칙이 **한 줄도 없는 것**을 실패로 만든다. 기존
`test_web_css_manifest.py` 는 *파일* 단위라(링크 순서·전수 등재·주석 균형) 등재된 파일 **안에서**
규칙이 편집돼 사라지는 것은 못 본다 — 세 테스트 모두 `.zone` 이 없는 상태에서 초록이었다.

그물은 **한 방향**이다(DOM → CSS). 반대 방향(CSS 에만 있고 생산자가 없는 죽은 선택자 —
아래 2건)은 초기 오탐 정리가 별건 규모라 세우지 않았고, 그 사실을 게이트 docstring 에
적어 뒀다. 조용한 축소가 아니라 선언된 축소다.

매체와 무관하다(게이트 조건은 `if self.data_path:` 하나). 사용자 상황에서는 **눌러도 아무것도
안 바뀐다** — 무해한데 겁주는 상태, 경보 인플레이션이다.

**계보가 곧 사망 근거다**: ⑴ 작업이 선언한 데이터를 풀에 자동등록한다(#18·#26 —
`default_dataset_ref` **자동 조준의 전제**) ⑵ 이름 기본값이 **파일 스템**이라 같은 파일 → 같은
이름은 필연 ⑶ 동명은 레지스트리가 자기-갱신으로 **조용히 통과**시켜 `opts` 가 덮이므로 확인을
승격했다(`:1583`). §5.3 이 ⑴의 **목적**(자동 조준)을 폐기하면 자동등록은 존재 이유를 잃고,
등록은 데이터 선택 면의 「이 데이터 고정」 **명시 행동** 하나로 남는다(§2.7 1행이 그 자리를 이미
만든다). **게이트가 발화하는 지점 자체가 없어진다.**

**막으려던 위험도 함께 사라진다.** 「매출」 항목의 참조가 갈아끼워져 *"그 이름을 쓰던 다른
작업들이 조용히 다른 데이터를 본다"* 가 이 게이트의 정당화였는데, 재편 뒤에는 **그 이름을 드는
작업이 0곳**이다(`Job.default_dataset_ref` 폐기 — 저장소 전수 대조상 풀 이름을 외래참조로 드는
곳은 그 필드 하나였다. 원장은 들지 않는다).

**짓지 않는 것**(편집 정책에 따라 조치 표를 **삭제**한다): 2축(이름·참조) 4분면 분류와 풀 전용
참조 역조회 함수. 남겨 두면 다음 사람이 곧 사라질 게이트의 문안을 다듬는다.

**폐기가 상속하는 의무 둘**:

- §2.4 「이 데이터로 신규 작업」의 선행이 §2.8 에서 **§5.3 으로 갈린다**(§1.1 순서 제약 갱신).
- §2.7 6행(이중 고정을 **회차 기억**으로 막음)은 이 라운드에서 **적힌 대로 착지한다**. 다만
  재편이 중복 판정을 **경로 기준**으로 바꾸면 같은 경로 재등록이 같은 항목이 되어 그 기억은
  잉여가 된다 — **그때 되깎는다**. 여기서 미리 지우지 않는 이유는 §2.7 이 먼저 착지하기
  때문이고, 폐기된 §2.8 이 「공짜로 준다」고 했던 `pinned_as` 백엔드 판정도 **오지 않는다**.

### 2.9 종료 가드 — 「문서 만들기」 성분 사망, 조용한 손실은 계약이다 (사용자 확정 2026-07-29)

②에서 승계. 원문 우선순위 ①세션 복원 → ②조용한 손실 → ③가드 조건 축소 중 **②로 확정**한다.

**③ 가드 조건 축소는 기각.** 술어(`data_zone.py:383-393`)는 이미 정밀하다 — 전체 선택·필터
정의 유래·마지막 생성분이 전부 무장에서 빠져 남는 것은 「손으로 고른 몇 행을 **안 쓰고**
나간다」 하나뿐이다. 더 줄이면 진짜 손실도 같이 놓친다. **처분 대상은 조건이 아니라 참여
자체다.**

**① 세션 복원을 안 고른 근거**(짓지 않기로 한 것도 기록한다): 복원이 이 가드를 실제로
닫으려면 술어 성분인 **선택 집합**을 덮어야 하는데, 선택은 **인덱스**이고 데이터 참조는
경로만 저장돼 실행 때 다시 읽힌다(`core/dataset_pool.py` 계약). 파일이 그사이 바뀌면 복원된
인덱스가 **다른 행을 조용히 가리킨다** — 가드 하나를 없애고 더 나쁜 침묵을 얻는 거래다.
정직하게 지으려면 행 수·열 헤더 지문 + 불일치 시 **복원 거절 재진술**까지 따라와 슬라이스
하나 규모가 된다. 계약 미착지분 `RestoreMountedData`/`SaveMountedDataRef`(§10.3)는 이
결정으로 **소비자를 잃는다**.

**사용자 계약**(원문 그대로) — *"명시적 종료 선언으로 받아들임 + 종료시 진행중 작업 정보를
보존하지 않는다는 사용자 계약"*.

| | |
|---|---|
| 죽는 것 | `screen_job.py:1928` `close_guard_reason` + 문안 「작업 화면의 완료하지 않은 선택」 |
| **사는 것** | `_guard_state`·`session_guard_for` — 홈 삭제 가드(#268)와 데이터 재겨눔·재연결 **사전 확인**(`_do_guard_state`)이 계속 소비한다. 소비자 셋 중 **하나만** 끊는다 |
| 무변경 | `close_guard_state` 참여 프로토콜·`Modal.confirm` 문안·`app.py` |
| 남는 참여자 | editor(「저장하지 않은 작업 편집」) · workbench(「미저장 연결 변경 또는 복사 진행」) — **둘 다 미저장 산출물**이지 재현 가능한 선택이 아니다. **국경이 여기다** |

**배제는 선언이어야 한다.** `test_close_guard_is_a_protocol_every_session_surface_joins` 의
`not_session` 표가 이미 그 자리를 지어 뒀지만, 그 표의 사유는 *"창을 닫아도 잃을 것이 없다"*
다 — job 은 **잃는다**. 같은 표에 넣으면 테스트가 거짓말을 하게 되므로 **두 번째 표**를
세운다(`silent_loss_by_contract = {"job": …}`). 「잃을 것이 없다」와 「잃지만 계약으로 조용히
잃는다」는 다른 선언이고, confirm-or-alarm 예외는 **숨기는 대신 표에 적히는 방식으로** 존재한다.

**예외의 성격 — 원칙에 예외 2호가 생겼다.** 기존 완화 조항(R-flow 결정 31: 전면 가시성 ∧
무반복 ∧ 검토 내장 표면의 「틀리면 보이는 추측」)과 **다른 계열**이다. 이건 추측이 아니라
손실이고, 정당화는 가시성이 아니라 **행위의 명시성**(X 클릭 = 종료 선언)이다. 두 예외를 한
조항으로 뭉치지 않는다 — 뭉치면 다음 조용한 경로가 둘 중 아무 쪽에나 기대어 들어온다.

### 2.10 두 확인 게이트 — 어휘를 가르고 지목을 준다 (사용자 확정 2026-07-29)

②에서 승계. 제보는 *"두 트리거의 차이를 소명하라"* 였고 §3 은 **소명을 요구했다는 사실이
결함**이라고 판정한 뒤 ③(확인 2면 재편 — 지금 §5.4)으로 넘겼다. 그 뒤 토의에서 처분이 갈렸다 —
**형상은 ③에 남기고 어휘·지목만 여기로 내린다.**

**국소로 가는 근거는 겹침의 수명이다.** 두 확인이 함께 서는 것은 **작업당 정확히 한 번**,
처음 만드는 작업에서뿐이다(§3 참고 · §10.12 판정 N: 업그레이드 비용은 작업당 1회). 한 번짜리
마찰에 표면 재편을 물리면 비용이 마찰보다 크다. 사용자가 잃는 것도 시간이 아니라
*"내가 방금 한 걸 또 하라는 건가"* 라는 신뢰다.

**증상을 원인 셋으로 가른다** — 셋 다 국소다.

| | 원인 | 처분 |
|---|---|---|
| ~~C1~~ | **이름이 같다.** 필드축 ack 와 규칙축 review 가 표면에서 둘 다 「확인」 | **어휘 분리** — **조치완료**(#335 · `5e0b7bb`) |
| C2 | **두 번째가 불시에 나타난다.** `_compose_gate` 는 서열 최상위 **하나만** 말하므로 빈 값 ack 를 다 끝낸 그 순간에야 검토 요구가 처음 뜬다 — 골대가 움직인다 | **보류**(아래) |
| ~~C3~~ | **내용이 같아 보인다.** 둘 다 "생성 전에 값을 본다" | **지목 신설** — **조치완료**(#335 · `5e0b7bb`) |

**C3 은 느낌이 아니라 사실 문제이기도 하다.** 첫 실행 드로어에서 거울이 못 보여주는 유일한
것은 **파일 이름 축**인데(거울은 필드×집계값뿐 — `_field_value_display`), 승인 버튼은
「결과 확인 완료」라고만 말해 그것을 안 가리키고 파일 이름은 `preview-foot` 구석에 가장 작게
선다. 그래서 사용자 눈에는 방금 거울에서 본 값을 한 번 더 보는 화면이다.

**어휘 — 「확인」은 필드축이 단독으로 갖고 규칙축은 「승인」으로 간다.** 아래 표 전체가
**착지했다**(#335 · `5e0b7bb`) — 4자리 모두 「승인」이고 필드축은 「확인」 그대로다.

| 자리 | 지금 | 바뀐 뒤 |
|---|---|---|
| 표지 `#jobReviewFlag` | `확인 필요` | `승인 필요` |
| 게이트 `review_gate_text`(`review_state.py:323`) | …「미리보기에서 결과를 **확인**해야 생성할 수 있습니다.」 | …「미리보기에서 나갈 **이름과 값을 승인**해야 생성할 수 있습니다.」 |

**어휘를 새로 짓는 것이 아니라 링1 이름을 표면으로 올리는 것이다** — 코드는 이미 `approve`·
`PreviewApproved` 불변식(§13-4)으로 그렇게 부르고, 표면만 두 축을 한 단어로 눌렀다. 부수로
버튼이 스타일 가이드 §84(버튼=동사)에 맞는다.

**탈락한 두 후보와 근거**(어휘는 점유 대조 없이 고르면 충돌을 옮길 뿐이다):

- **「검토」** — `work_mode.py:44` 「온나라 기안 **검토**·복사」가 점유. 코드 이름(`review_state`)
  과는 맞지만 표면에서 다른 축에 이미 가 있다
- **「확정」** — 매핑 축이 점유(*"모든 행을 검토·확정해야 저장으로 진행"*, `COPY_STYLE_GUIDE` §76)

**곁다리로 함께 풀리는 충돌**: 라이브러리 탭 「확인 필요」(후보 건전성 — `work_candidates.py`)와
`#jobReviewFlag`(규칙축)가 지금 **글자까지 같다**. 규칙축이 「승인」으로 옮겨가면 별도 조치
없이 사라진다.

**C2 보류 근거.** 잔여를 미리 보이려면 게이트가 목록이 되는데, 게이트는 **단일 산출**이 계약
이고(UD-06: 버튼 비활성 + 인라인 사유 하나) 실제 서열은 드리프트·파일명·빈 값 ack·저장 폴더·
선택 0건·검토 요구까지 최대 여러 단이라 "남은 것 전부"는 국소수술이 아니게 된다. C1·C3 착지
뒤에도 골대 느낌이 남는지 실앱 한 바퀴로 재평가한다.

**파일 이름의 자리는 이번에 옮기지 않는다.** `preview-foot` → 상단 승격은 C3 을 더 확실히
하지만 드로어 배치를 건드리므로 §2.2 와 함께 판단한다. 이번 조치는 **문안까지**다.

**미조치 항목의 기록**(§2.3 마지막 행 — 「아직 한 번도…」가 「확인할 변경」 캡션 아래 있는 것).
사용자 확정으로 **미조치**다. 근거는 거슬림이 실재하나 해가 작다는 것. 짓지 않기로 한 안 셋을
남긴다 — 다시 발견될 때 세 번 세지 않으려고 적는다:

1. 캡션을 사유별로 갈리게(링1이 캡션 문안까지 소유) — 페이로드 키 1개 신설, 문안 3벌 유지
2. 캡션 중립화(「확인할 것」) — rows 가 진짜 before/after 변경일 때 그 이름을 잃는다
3. reason 을 섹션 밖 드로어 상단으로(증거 섹션은 증거가 있을 때만) — 정적 DOM 계약 갱신

3안이 가장 정직했다(reason 은 섹션의 부제가 아니라 드로어 전체의 전제이고 게이트와 문장을
공유한다). §2.3 의 note 0건 비움과 합치면 첫 실행에서 증거 섹션이 통째로 비어 자연히 사라지는
것도 그 안의 소득이었다. **비용 대비로 접었을 뿐 판정이 뒤집힌 것이 아니다.**

**삭제·개명이 상속하는 의무**: `app.py:2156` 셀프테스트 스텁이 게이트 문안 **사본**을 들고 있어
함께 갱신한다. 표지 텍스트는 정적 DOM 계약이 잡고, 링1 함수·클래스 이름(`review_state`·
`review_gate_text`·`ReviewRequirement`)은 **바꾸지 않는다** — 표면 어휘 교체지 판정 축 개명이
아니다.

무해·허용 10건은 전부 자기 폭만 갖는다(`.btn` +2.22 · `.navbtn` +1.68 · `button.pill` +1.19 ·

**판정 기준은 「컨테이너를 채우는가」다**(폭 자체가 아니라). 채우는 요소는 이웃·머리와 기준면을
공유하므로 중심 축소가 곧 정렬 이탈이다. `.ctx-menu button` 이 140px 로 작은데도 파손인 이유이고,
`.btn` 이 148px 로 비슷한데 무해한 이유다.

**같은 계열 셋을 더 찾았다 — 「선언은 살고 결과는 죽는다」.**

- **`.job-item`** — 눌림 계약 4자리에 이름이 있는데 **산출자가 웹 자산 전체에 0곳**이다
  (F2 PR-B 로 좌 master 목록 사망). 평면 계약이 죽은 선택자를 부양했다.
- **`badge.missing_press`** — `design_tokens.json` 에 **두 테마 다 손으로 지정**돼 있는데
  `gen_design_tokens.py` 매핑이 없어 `tokens.css` 에 **방출조차 안 됐다**. 사용처 0곳. 즉 눌림을
  배경 축으로 하는 설계가 **이미 있었고 버려졌다** — `scale` 이 그 빈자리를 대신 채웠다.
- **토큰 게이트의 구멍** — `test_design_tokens.py` 는 라이트↔다크 패리티와 라이트→CSS 방출을
  보는데 **JSON 키 → 매핑 존재**는 아무도 안 본다. 그래서 위 고아가 조용히 살았다.

**조치**(착지): 선택자 목록을 **「작은 조작 상자」**(`scale(.97)` 유지 10건)와 **「컨테이너를
채우는 표면」**(4건)으로 가르고, 후자는 hover 가 이미 쓰는 **배경 축**의 다음 단으로 눌림을
말한다. `transform-origin:left` 로 옮기는 안은 기각 — 폭이 여전히 변해 열 정렬 이탈이 남는다.
`translateY(1px)` 도 표에서는 이웃 행과 1px 겹쳐 보여 택하지 않는다.

|---|---|---|
| `.job-grp-head` · `.ctx-menu button` | `var(--n-pressed)` | 팔레트에 있던 hover 램프의 다음 단 |
| `.mir-row.miss td` | `var(--fb-missing-press)` | **고아 토큰 회수** — `gen` 매핑 3줄 추가로 방출 |

| `.jobtb tbody tr.on` | `color-mix(--a-sel 88%, --a-ink)` | 선택 행은 이미 100% 라 잉크를 얹는다 |

**색은 소유자 파일이 낸다**(`job.css`·`jobdata.css` 의 hover 규칙 옆), **지속시간만 `base.css`
모션 층**이 소유한다. 색을 공용 층으로 끌어오면 §2.1 과 같은 모양이 된다 — 공용 규칙이 곁의
규칙을 덮고, 되읽을 자리가 소유자에서 멀어진다.

**부수 소득**: `reduced-motion` 에서 이제 **전이만** 끈다. 종전엔 이 표면들의 눌림이 통째로
사라져 모션을 끈 사람에게 눌림 피드백이 **0** 이었다 — 그 강등이 이 결함의 로컬 미재현 원인
이기도 했다(개발 기기가 거기 살았다). 색은 이동이 아니라 상태 표지이므로 즉시 남는다.

**검사가 이 결함을 고정시켰다.** `test_interaction_responsiveness.py`
`test_press_feedback_covers_round_trip_surfaces_and_reduced_motion` 이 8개 선택자 **전부**에
눌림 표지가 있어야 한다고 단언했다 — 규칙의 **존재**는 강제하는데 **기하 결과**는 못 본다.
§2.1 의 그물이 「DOM 이 내는 class 에 규칙이 없다」를 잡았다면, 없던 그물은 **「규칙이 있는데 그
결과가 틀렸다」** 쪽이다.

**검사 복구**(착지) — 셋으로 갈랐다:

| 층 | 파일 | 맡는 것 |
|---|---|---|
| 정적(존재) | `test_interaction_responsiveness` | 두 갈래 각각에 표지 + 강등이 있는지. `.job-item` 부활 금지 |
| 정적(갈림) | `test_web_press_geometry` 앞부분 | `scale` 목록이 **선언과 정확히 같은지** — 새 표면이 결정 없이 평면으로 늘면 멈춘다. 죽은 선택자 산출자 0건 재확인 |
| 실렌더(결과) | `test_web_press_geometry` + `_press_probe` | 실 CSS 를 링크한 최소 문서에서 `:active` **유지 중** 좌변 이탈 ≤ 1px. `reduced_motion` 두 값 강제로 양성·음성 대조 |

곁들여 **주석이 규칙으로 세어지던 것을 고쳤다** — 계약 문서화를 위해 주석에 죽은 선택자 이름을
일부러 남기므로, substring 단언 전에 산문을 걷는다(`_web_css.strip_comments`). 그리고
`test_ux_css_round` 의 인접 검사(`:active:not(:disabled){transform:scale(`)를 **두 사실로
갈랐다** — 그 한 덩어리는 선택자 목록의 **꼬리가 무엇인가**에 검사를 묶어, 규칙이 그대로 있는데
목록이 갈리자 빨간불이 났다.

**전제를 시끄럽게 확인한다.** CI 에 `Press-geometry browser precondition` 단계를 세워 설치 Chrome
부재를 테스트 안쪽 오류가 아니라 한 줄로 말하게 하고, 세 옵트아웃 변수를 CI 에서 **걷고** 돌린다
(`test_quality_workflow` 가 그 형상을 진다).

**후속 규칙 — 개발 기기가 모션을 꺼 두면 모션 층은 검사된 적이 없다.** 로컬 미재현은 우연이
아니라 구조다: 이 기기는 `SPI_GETCLIENTAREAANIMATION=False` 라 Chromium 이
`prefers-reduced-motion: reduce` 를 보고하고 `base.css:135-137` 이 `transform:none` 으로 끈다.
즉 #194 모션 토큰 층 전체(`:active` 눌림 · `@starting-style` 팝 · 모달 `scale`)가 이 기기에서
**한 번도 돈 적이 없다** — 101 하니스 스크린샷·selftest·눈검증이 전부 「모션 없는 세계」의
산출이었다. 계측 층의 조용한 오류 그 자체라, 프로브를 그냥 붙이면 **영영 초록**이다. 게이트는
`prefers-reduced-motion` 을 **명시로 강제**하고 두 값으로 각각 재서 음성 대조를 먼저 세운다.
실앱(WebView2)은 OS 설정을 따르므로 강제의 매체는 **Playwright + 설치 Chrome 의 `reduced_motion`
컨텍스트**다 — 테스트가 사용자 OS 설정을 변이하지 않는다는 규율이 그 선택의 근거다.

## 3. ② 재등급 — 「실재하지 않음」이 아니라 「결함 소재가 다르다」

②를 다시 세면 **조치 0인 것은 1건뿐**이다. 나머지는 설계 판정이 살아남되 사용자가 그렇게
읽었다는 사실이 **표면의 실패 증거**이므로, 소재만 옮겨 ①·③으로 재배치된다.

| 항목 | 살아남는 판정 | 그럼에도 남는 결함 | 재배치 |
|---|---|---|---|
| TXT에 미리보기 불필요 | §10.15 판정 J가 배제 선언했고 거울 존도 `display:none`(`job.js:465`) | 없음 | **조치 0** |
| 「선택한 작업」 불필요 | 템플릿 파일명·열기 어포던스·재연결 경보가 실질 | 중복인 작업명이 굵고(`job-head-title`) 실질인 템플릿이 `muted` — **위계 역전** | §4에서 **확정** — **미착지** |
| ~~되돌리기 `↩` 불필요~~ | 유일한 행 단위 자동 제안 복귀 경로. 대체재로 지목된 「일괄 초기화」는 **존재하지 않는다**(「모두 해제」는 확정만 풀고 수동 지정은 남는다) | 아이콘이 `↩`(undo)라 **되돌리기로만 읽힌다** — 같은 사용자가 「수동 재추천 버튼이 없다」고 따로 요청했다. **기능이 이름에 가려졌다** | **① 승계**(§2.6 확정) — **조치완료**(#334 · `3469d44`) |
| 파일 찾아보기 ≡ 직접등록 | 직접등록은 파일 대화상자가 아니라 이름·경로·시트·메모 **수동 입력 폼** | 그 폼 **안의** 「찾아보기…」가 같은 네이티브 피커를 열고 라벨이 「파일 찾아보기…」/「찾아보기…」로 거의 같다 — **표면 어휘상으로는 관찰이 정확하다** | **① 승계**(§2.7 확정) — **미착지** |
| 등록 후 바로 메인으로 나감 | 직접등록은 모달을 유지한다(「이 데이터 사용」 2클릭 = 제안대로) | 본 것은 「파일 찾아보기」 경로이고 **그 경로엔 고정 기회가 없이 지나간다** | **① 승계**(§2.7 확정 — 위 항목과 **한 조치**) — **미착지** |
| 「아직 한 번도…」 불필요 | 검토를 요구하는 **이유 문장** | 자리가 틀렸다 (§2.3) | **미조치 확정**(§2.10 말미에 짓지 않은 안 셋) |
| ~~두 트리거 차이 소명~~ | 필드축 ack(`run_state.py:512`) vs 규칙축 검토(`review_state.py:148`) — 다른 축이 맞다 | **소명을 요구했다는 사실이 결함이다.** 거울 "눌러서 **확인**해야 생성할 수 있습니다" / 드로어 "결과 **확인** 완료" — 같은 동사가 두 축에 겹친다 | **① 승계**(§2.10 확정) — 어휘·지목만 **조치완료**(#335 · `5e0b7bb`). **형상은 §5.4 에 남는다** |
| 종료 가드가 항상 뜬다 | 판정은 조건부(`data_zone.py:351 _selection_guard`) | **정상 워크플로가 정확히 그 조건**(몇 행 수동 선택 → 생성 안 하고 종료)이라 실질은 맞다 | **① 승계**(§2.9 확정) — **미착지** |

**후속 규칙 — 소명이 서면 그 소명이 결함의 증거다.** 계약 문서로 변호할 수 있다는 사실은,
앱을 쓰는 사람이 그것을 알 길이 없다는 뜻이다. ②를 「기각 목록」으로 닫으면 진짜 결함을 놓친다.

### 참고 — 두 확인 게이트의 관계 (반복 질문 대비)

```
드리프트(danger) > 파일명 토큰(danger) > 「본문 확인」 ack(warn)
  > 전제조건(warn) > 「미리보기」 검토 요구(warn) > 열림
```

- **본문 확인(거울)** = 필드축. 선택분에서 값이 빈 필드 중 확인 안 된 것 (`run_state.py:512`)
- **미리보기(드로어)** = 규칙축. 저장된 규칙 지문 vs 마지막 완주 기준선의 차이 (`review_state.py:148`)

두 확인이 겹치는 건 **처음 만드는 작업에서만**이다 — 한 번 완주하면 검토 요구는 영구히
조용해지고 ack만 남는다(§10.12 판정 N: "업그레이드 비용은 작업당 1회"). 따라서 "정상 루프에서
보일 일 없다"는 관찰은 **미리보기 쪽엔 참, 본문 확인 쪽엔 거짓**이다.

## 4. 판정 — 「선택한 작업」 존 사망과 후보 카드 승계 (사용자 확정 2026-07-29)

### A. 「선택한 작업」 존(`index.html:336-341`)은 사망한다

근거는 **「메인을 어설픈 계기판으로 만드느니 계기판을 계기판으로」**(사용자 확정). 실측이
이를 강화한다 — 메인의 어포던스는 이관 대상이 아니라 **세 번째 사본**이었다:

| 기능 | 메인 존 | 라이브러리 상세 | 편집기 「템플릿」 탭 |
|---|---|---|---|
| 템플릿 이름 | O | O (`library.js:290`) | O |
| 열기·폴더에서 보기 | O | **없음** | O (`editor.js:548`) |
| 「템플릿 다시 연결…」 | O | O (`library.js:271`) | — (공용 `Relink`) |

라이브러리 경보 문안이 이미 같은 문법을 쓴다 — *"템플릿이 연결되지 않은 작업 N건이 있습니다.
「확인 필요」 보기에서 조치하세요."* **경보는 여기, 조작은 저기.**

**사망 조건 점검표** — 전 행이 새 거처에서 도달 가능함을 확인한 뒤에만 지운다:

| 죽는 것 | 승계처 |
|---|---|
| 작업명 표시(`#jobHeadTitle`) | 후보 카드 `.active` 하이라이트 — **이미 존재** |
| 템플릿 파일명(`#jobHeadTpl`) | **활성 카드**의 확장 부제 (판정 B) |
| 열기·폴더에서 보기(`PathTrack`) | **활성 카드 ⋮** (판정 B) + **라이브러리 상세에 신설** — 계기판의 짝. 현재 `library.js`에 `PathTrack` 0건 |
| 「템플릿 다시 연결…」 버튼 | 경고 카드의 **기본 클릭 대체** (판정 D) |
| `template_missing` 경보 | 카드 **「연결 상태」** 텍스트 + 경고색 (판정 C) |
| 「템플릿 경로가 비어 있습니다…」 | 같은 「연결 상태」 축 |
| 「문서 작업을 선택하면…」 빈 상태 | 후보 구획 빈 상태가 이미 소유 |

### B. 카드 ⋮ 와 확장 부제는 활성 카드에만 선다

§10.1 S1의 카드 항목(`이름·방식·연결 상태·마지막 성공 실행·즐겨찾기·⋮`) 중 **⋮ 와 연결
상태는 계약이 자리를 잡아뒀는데 안 지어진 칸**이다 — `candCard`는 이름·방식·마지막 실행·별만
구현한다. 전 카드에 주면 side-card에 ⋮ 다섯이 서고, 이 계열 버튼은 `visibility:hidden` +
hover 노출이라 발견성이 나쁘다(F8 주석이 *"노출 규칙이 없으면 기본 hidden 이라 영영 안
보인다"*고 자백). 활성 카드만 확장하면 죽는 존의 의미론(**선택된 하나의 정체**)을 카드가
그대로 승계한다.

### C. 「연결 상태」는 텍스트가 정본이고 색은 강조다

`candCard` 주석이 이미 계약을 적었다 — *"색만으로 방식을 구별하지 않는다(텍스트가 늘 함께
선다)."* 따라서 경고색 하이라이트는 **「연결 상태」 신설과 한 묶음**이다. 존을 죽이는 것과
연결 상태를 짓는 것은 분리할 수 없다.

### D. 재연결은 메뉴 항목이 아니라 기본 클릭의 대체다

재연결이 필요한 카드는 경고색으로 서고, 클릭하면 선택 대신 **안내와 함께 재연결로
리다이렉트**된다. 부수 규칙 셋:

- 활성 + 경고가 겹치면 **경고가 이긴다** — 선택 사실은 다른 단서로도 서지만 차단 사유는
  여기서만 말한다
- 클릭 의도(선택)와 실제 동작(재연결)이 다르므로 **왜 다른지 재진술**한다(다이얼로그가 겸한다)
- 재연결 성공 뒤 **이어서 선택**한다 — confirm-or-alarm 완화 조항(전면 가시성·틀리면 즉시
  보임). 순서는 브리지 발신 규약: 재연결 커밋이 성공한 **뒤에** 선택이 한 체인으로 나간다.
  실패하면 선택하지 않고 카드는 경고로 남는다

### E. needs 리다이렉트는 2분기다 — §18.7 6분기 중 나머지 넷은 짓지 않는다

계약 표(`docs/core-workflow.md` §18.7)를 펴고 master 실측과 대조한 결과:

| # | 계약 원인 | 사용자 행동 | master 실측 | 처분 |
|---|---|---|---|---|
| 1 | Binding drift | 연결 복구 | needs 사유로 없음 — 선택 후 게이트가 danger 차단 + `openEditForRepair` | **이미 다른 층에서 풀림** |
| 2 | 복원 가능한 `default_dataset_ref` | 기본 데이터 사용 | #53-A 자동 조준(`data_notice`, §8.2 ③ 현행 유지) | 데이터 축이 소유 |
| 3 | 끊어진 **데이터** 참조 | **데이터** 참조 다시 연결 | 데이터 선택 다이얼로그 고정 행 「다시 연결…」(F1) | 데이터 축이 소유 |
| 4 | **다른 데이터 구조**의 저장 작업 | 이 템플릿으로 새 작업 | **master `needs_action`의 유일 원인** — `missing = 현재 데이터에 없는 필수 소스 키`(`work_candidates.py:73-75`) | **짓는다** |
| 5 | Template-only 자산 | 새 문서 작업 만들기 | 후보엔 작업만 뜬다 | 후보 목록의 정체를 바꾸는 **별개 결정** |
| 6 | Job/Template 손상 | 지원 범위 확인 | `excluded(unsupported)` + 손상 격리 | 계약이 **리다이렉트를 금지**: *"연결 문제로 추측하지 않고 실제 점검 필요 상태 표시"* |

4행의 목적지는 **`document_browser_new_work`** 인데 이 사유는 `DEFERRED_ENTRY_REASONS`에
남아 fail-closed 차단 중이다. F8은 종결됐으므로 **그 줄을 지우는 것이 배선의 전제**이고,
그 한 번의 해제가 needs 카드 리다이렉트와 「이 데이터로 신규 작업」(§2.4)을 **동시에** 연다.

따라서 needs 구획은 사유별 2분기를 갖는다:

| 사유 | 「연결 상태」 문안 축 | 클릭 목적지 |
|---|---|---|
| 데이터 구조 불일치 | 없는 열 열거 | 새 작업 마법사 |
| 템플릿 부재 | 템플릿 없음 | 재연결 |

### F. 템플릿 부재를 후보 축에 올리는 것은 계약과 다른 배치다 — 근거는 전제 차이

§18.7 6분기에 **템플릿 재연결은 없다**(3행의 「다시 연결」은 **데이터 참조**다). §18.4가
선을 긋는다:

> `available`은 최소 Binding 호환성일 뿐 (…) **Template 읽기**, 구조 drift, 파일 이름 토큰
> (…)은 작업 선택 뒤 권위 있는 `validateRun`에서 따로 검사한다.

즉 판정 D는 계약의 미구현분을 채우는 것이 아니라 **다른 배치를 택하는 결정**이며, §10.0의
「계약이 이긴다」에 대한 **명시적 예외**다. 근거는 전제가 달라졌다는 것이다: 계약이 후보 축
밖에 둔 이유는 v6 세계에서 Template 읽기가 비싼 검사였기 때문인데, master는 이미 그 판정을
싸게 갖고 있다(`library_health`의 `missing_template_count`). **눌러본 뒤에 차단하는 것은
뒤늦은 경보다.**

「계약 항목을 짓기 전에 그 문제가 여기서 이미 어떻게 풀리는가를 센다」 규칙의 **역방향 표본** —
세어 보니 계약보다 **더 이르게** 풀 수 있었다. lab `core-workflow.md` §18.4 쪽에 정정 표기를
넣을지는 열어 둔다.

### 5.3 저장소 정체성 — 데이터 축은 **경로가 정체성**, 작업↔데이터 결속은 폐기

§2.8 을 파다가 *"풀이 이름을 키로 드는 게 이상하다"* 는 질문이 나왔다. 첫 판정(2026-07-29)은
「이름=키 유지 · id 기각」이었고 **2026-07-30 토의에서 데이터 축에 한해 뒤집혔다.** 그 결과
§2.8 이 폐기됐으므로 이 절은 미결 설계가 아니라 **라운드가 낳은 판정**이다.

**관찰 — 한 저장소에 식별 관례가 셋이다.**

| 대상 | 식별 | 링크를 거는 쪽 | 판정 후 |
|---|---|---|---|
| 작업 | 이름(slug 파일명) | — | **불변** |
| 데이터 참조 | 이름(slug 파일명) | 작업 → 데이터 = **이름**(`default_dataset_ref`) | **경로+시트가 정체성 · 링크 폐기** |
| 템플릿 | **절대경로** | 작업 → 템플릿 = `template_path` | 판정 B(상대키) 그대로 |
| 템플릿(그룹 지정) | **홈 상대경로** | 그룹 → 템플릿 = `rel_key(path, root)`(`template_groups.py:44`) | **불변** |

**판정 A(개정) — 이름=키는 유지하되 적용 범위가 작업·템플릿 축이다. 데이터 축에서는 철회한다.**

첫 판정의 근거는 이식이었다 — 저장 관례(`slug` 파일명 + `ensure_ascii=False` + `indent=2`)와
위치-불가지가 겨눈 것이 **「폴더가 곧 이식 단위」** 이고, 코드도 그렇게 적어 뒀다
(`screen_editor.py:1815-1816`): *"등록 실패해도 참조 이름은 안정적이라 사용자가 그 이름으로
수동 등록하면 링크가 완성된다"*.

그 논거는 참이지만 **데이터 축에 잘못 배치됐다.** 이식해야 하는 것은 템플릿+매핑이고(판정 B 가
이미 그렇게 말한다) **남의 PC 에 내 엑셀 파일은 없다.** 데이터는 이식 대상이 아니라 각자
**자기 것을 연결하는 것**이다. 같은 절이 템플릿 축에서는 자동 파일명 매칭을 *"다른 폴더 동명
파일 오연결로 악명"* 이라며 기각해 놓고 데이터 축에서는 그 기제를 이식 근거로 든 모순도 여기서
풀린다 — **두 축 모두 이름 자동 결속을 안 쓴다**로 일관된다.

**판정 C — 데이터 축 정체성은 `normcase(abspath(path)) + sheet` 다.**

- `name` 은 **순수 라벨**로 강등한다 — 중복 허용·개명 자유·정체성 무관.
- `_slug` 파일명과 `guard_slug_collision` 의 **데이터셋 소비자가 소멸**한다(작업 축은 그대로).
- 시트가 축에 드는 것은 새 발명이 아니다(#33) — 같은 워크북의 다른 시트는 다른 데이터다.

**판정 D — 작업↔데이터 결속(`default_dataset_ref`, #53-A)을 폐기한다.**

이 필드는 **v6 데이터-우선 재작성을 살아남은 작업-앵커 잔재**다. 앱의 정본 방향은 이미
「데이터를 고르면 가능한 작업이 선다」이고(`gui/work_candidates.py`), 반대 방향으로 흐르는
배선은 이것 하나뿐이었다. 이름 정체성 문제가 여기서만 터진 이유이기도 하다.

| | |
|---|---|
| 죽는 것 | `Job.default_dataset_ref` · `_auto_aim_default`(`screen_job.py:1856`) · `_do_prefer_work` 의 `default_data` 분기(`:1761`) · 저장 시 데이터 **자동등록**(#18·#26)과 그 게이트(`screen_editor.py:_dataset_gate`) |
| 사는 것 | `source_keys()` 계약 · `compatibility_for`/`rank_available` 후보 판정 · 세션 소유 마운트 데이터 · 「이 데이터 고정」 **명시 등록** |
| 바뀌는 것 | 작업을 먼저 고르는 진입점(라이브러리 「문서 만들기에서 사용」)은 **데이터 선택을 반드시 지난다** — `_do_prefer_work` 는 「보관 후 안내」 하나로 단순해진다. F2 PR-B 판정 I 가 걱정한 「#53-A 도달 불가능」은 **#53-A 자체가 죽으므로 소멸**한다 |

**id 축(`dataset_id`) 기각의 근거는 「이름이 좋아서」가 아니라 「지킬 것이 없어서」다.**
`dataset_pool_state.update_excel_reference` 계약이 *"기존 항목의 참조(kind+opts)만 갱신한다
(**수명 보존**)"* 라고 못박는다 — **내용물 교체가 정상 수명 사건**인 개체다(월별 파일이면 매
사이클 갈아끼운다). 불변 id 는 삭제·재생성과 relink 를 구분해 주지만 **끝 상태가 같다.** 게다가
결속이 사라지면 정체성을 오해할 **소비자 자체가 없다** — 저장소 전수 대조상 풀 이름을
외래참조로 드는 곳은 `default_dataset_ref` 하나였다(원장은 들지 않는다).

**함께 기각 — 풀 항목의 스키마 지문 캐시 필드.** 「작업 → 후보 데이터」 방향이면 풀 항목 N개의
헤더가 필요해 캐시가 정당했다. 방향이 **데이터 → 작업**이면 읽는 파일은 사용자가 방금 고른
1개뿐이고 어차피 마운트하며 읽는다. **이 재편의 신규 durable 필드는 0개다.**

**이미 서 있는 것 — 이 판정은 신설이 아니라 잔재 제거다.**

| 모델 | 실측 |
|---|---|
| 작업은 데이터가 아니라 **스키마**를 기억한다 | 이미 참 — `Job` 에 데이터는 없고 `source_keys()` 가 계약. **유일한 이물질이 `default_dataset_ref`** |
| 데이터를 고르는 순간 스키마를 읽어 **가능한 작업을 제시**한다 | 이미 구현 — `compatibility_for`(`missing = source_keys − 현재 열`) + `rank_available` + 「확인 필요」가 빠진 열을 재진술 |
| 즐겨찾기는 **작업 소유** 속성이다 | 이미 그렇다 — `Job.favorited_at` 이 후보 정렬의 **1차 계층**(`TIER_FAVORITE`). 데이터별 즐겨찾기는 존재한 적 없다 |
| 데이터 목록은 **경로로** 관리된다 | **여기만 실제 변경** — 지금은 이름 slug 가 키고 경로는 내용물이다 |

**뒷문 금지**: 「이 데이터로 자주 쓰는 작업」류의 **데이터별 선호**를 나중에 만들면 그것이 곧
`default_dataset_ref` 의 재발명이다. 데이터↔작업 결속은 어느 방향으로도 다시 들이지 않는다.

**사용자가 내주는 것**(명시 확인, 2026-07-30): **「작업을 열면 데이터가 이미 서 있다」가
사라진다.** 매달 같은 파일을 쓰는 사람도 데이터를 고르고 후보에서 자기 작업을 고른다.
완화는 둘 — ⑴ 마운트 데이터는 **세션 소유**라 작업 전환에서 생존하므로 요구는 **세션당 1회**다
(지금도 자동 조준은 `datasource is None` 일 때만 돈다) ⑵ 후보가 1건이어도 **자동 결속하지
않고** 미리 골라 둔 채로 제시한다 — 여기서 자동으로 붙이면 원칙이 다시 샌다.

**마이그레이션은 무손실이 아니다.** 기존 `.dataset.json` 은 `opts.path` 를 들고 있어 새 키로
재배치되지만, **다른 이름·같은 경로 2건**은 병합 판정이 필요하다(조용히 하나 버리지 말고 loud
재진술 후 사용자 확정). 작업의 `default_dataset_ref` 는 마이그레이션이 아니라 **폐기**다 —
「이 작업이 지난번 쓰던 데이터」 정보가 사라진다.

**판정 B — 결함은 템플릿 축이다.** 레지스트리는 위치-불가지인데 **내용물이 위치에 묶여 있다.**
홈을 옮기면 작업의 `template_path` 가 전부 깨진다. 증거가 경보 문안에 있다 — 라이브러리는
*"템플릿이 연결되지 않은 **작업 N건**"* 이라고 **작업 수**로 센다. 간접층이 있었다면 데이터처럼
「참조 1건」이었을 것이다. 데이터 축은 간접층 덕에 이식성을 갖고, 템플릿 축은 못 갖는다.

**처방 — 템플릿을 데이터 쪽에 맞춘다**(반대가 아니라):

- `Job` 에 **라이브러리 루트 상대 POSIX 키**를 가산 필드로(`조달/공고서.hwpx`). 매체는 접미사
  파생이 이미 계약(`core/job.py:204`)이라 **루트 선택도 확장자로** 하면 새 필드가 필요 없다
- 관례를 새로 만들지 않는다 — `rel_key` 가 이미 그 값을 만들고 그룹 지정이 쓴다. **표면도 이미
  키로 말한다**(`screen_editor.py:574`). 저장만 경로다
- **폴백 정책만 다르다**: `rel_key` 는 루트 밖이면 파일명으로 폴백하는데, 작업 링크에서 그
  폴백은 **다른 폴더의 동명 파일에 조용히 붙는다**. 작업용 변환은 폴백 없이 실패하고 기존
  절대경로를 유지한다 — "이 작업은 이식 대상이 아니다"를 정직하게 남긴다
- 마이그레이션 없음: 읽기는 새 키 없으면 옛 경로로 폴백, **저장할 때만** 승격. 읽는 김에 디스크를
  고치지 않는다(조용한 변이 금지)
- 화면 변화 0 — `PathTrack` 어포던스는 해석된 절대경로를 받는다. `template_media`·`work_mode`·
  `library_mode_of` 는 확장자만 보므로 무영향

**웹 표준 대조**(2026-07-29 조사) — 도출한 안이 확립된 해법과 일치한다:

| 우리 문제 | 표준 해법 |
|---|---|
| 참조가 PC에 묶임 | **path variable / named root + root-relative**(IntelliJ: 프로젝트는 변수 **이름**만 저장, 값은 각 머신 소유. AutoCAD xref: 공유·이동 프로젝트는 상대경로가 기본) |
| 남에게 전달 | **Collect / Package**(Ableton *Collect All and Save*, InDesign *Package*) — 평소엔 참조, 전달 시 자산을 모아 자기완결 폴더로. **§5.2 broad 안이 이 기능의 이름 없는 재발견** |
| 끊긴 참조 복구 | 자동 파일명 매칭은 **다른 폴더 동명 파일 오연결**로 악명(Pro Tools·Resolve·Premiere) → 수동 확인 선호. 위 폴백 거절 규칙과 같은 결론 |

표준은 경로를 **버리는** 것이 아니라 경로에서 **기계 고유 부분만 이름으로 치환**하는 것이다 —
id 키 안이 이 계열의 해법이 아닌 이유이기도 하다. **이 대조는 템플릿 축(판정 B)의 것이다**:
표의 세 문제는 전부 *"남에게 전달한다"* 를 전제하는데, 데이터 파일은 애초에 전달 대상이 아니라
대조 밖이다. 다만 3행(자동 파일명 매칭 = 오연결로 악명)의 결론은 이제 **두 축에서 같다**.

**범위**: 이 절의 **판정 A(개정)·B 는 U2 문서가 소유**한다 — §2.8 폐기와 §2.4 선행 갈림이
여기서 나오기 때문이다. 반면 **판정 C·D 의 구현은 U2 밖 「데이터 축 재편」 슬라이스**이고,
판정 B(템플릿 상대키)는 여전히 **부트스트래핑 broad 안의 선행**이다(§5.2). 이산 조치(필드 폐기 ·
풀 키 교체 · 마이그레이션 병합 확인 · 자동등록 제거)는 **GitHub 이슈**가 진다.

### 5.4 확인 2면의 형상 — 합칠 짝은 정해졌고 시점만 남았다

§2.10 이 어휘·지목을 가져갔으므로 여기 남는 것은 **면을 합칠 것인가**뿐이다. 토의에서 짝과
근거는 확정됐고 **착수 시점만 미결**이라, ③에 두되 판정은 적어 둔다.

**실측 — 같은 일을 하는 pane 이 셋인데 세 표면에 흩어져 있다.**

| pane | 무엇을 보이나 | 온나라 작업대 | HWPX 「문서 만들기」 |
|---|---|---|---|
| 규칙 | 필드 연결·표시 | 좌 pane(`wb-left`) | **편집기** — 별도 몰입 화면 |
| 레코드 | 이 한 건의 실물 | 우 pane(`wb-right`) | **미리보기 드로어** — 모달 |
| 집합 | 선택 N건을 접은 상태 | **없다**(건별 큐라 불필요) | 거울 존(인라인) + 펼침 면 |

**U2 안(편집기 + 드로어 = 작업대 동형)은 기각한다.** 작업대 좌 pane 은 「저장하지 않은 변경」을
굴리는 pane 인데(`#wbDirtyNote`·`#wbSaveRules`), HWPX 쪽에서 그 축의 이름이 `runOverrides`
이고 **§10.14 에서 기각·사망**했다. 되살려도 안 붙는다 — HWPX 승인은 규칙 지문에 결속돼
있어(`approval_key = rules_key|selection_key`) 같은 면에서 규칙을 고치면 방금 받은 승인이
자동 무효가 되고, 한 면 안에서 승인→편집→무효→재승인이 돈다. 작업대는 승인 게이트가 없어
(복사는 건별) 그 상극이 안 생긴다. **형상만 베끼면 죽인 개념이 승인 모델과 부딪친다.**
편집 왕복 자체는 이미 계약으로 지어져 있다 — `previewEdit` 이
`return_context:{surface:"preview", reopen_drawer:true}` 와 증거 「보고 있던 행」을 들고
나가고 행별·파일 이름 「수정」은 편집기 해당 탭까지 딥링크한다(§10.14.3).

**U1 안(거울 + 드로어)이 합칠 짝이다.** 둘은 **같은 산출의 두 투영**이다 — 값 출처가 하나이고
(`screen_job.py:1338`: *"선택분 매핑 적용은 1회 — 파일명 미리보기와 거울 값이 공유"*), 거울은
선택 N행을 한 열로 **접은** 것, 드로어는 그중 한 행을 **편** 것이다. 접기·펴기는 한 면에서
표현되는 것이 정상이고, 그러면 이 항목의 원래 목적(**두 축을 나란히 놓아 차이를 보이게**)이
따라온다.

**원문 안의 정정 — 2탭이 아니라 2 pane 이다.** 처음 적힌 「한 오버레이 2탭」은 두 축을 **동시에**
못 보게 하므로 목적과 상충한다. 골격 비용은 이미 지불돼 있다: 펼침 면 `#jobConfirmSheet` 이
벌써 `sheet-duo` 2 pane 이고, **거울의 실 DOM 을 슬롯으로 이동**하는 기법이 구현돼 있다
(`index.html:714-725`) — 드로어의 레코드 pane 도 같은 방식으로 옮긴다. 인라인 거울 존은
**존치**한다(§10.6 결정 3: 거울은 `ack_field` 게이트를 푸는 유일 표면이라 숨기면 차단된 사람의
출구가 사라진다).

**이 재편의 진짜 정체는 렌더러의 선행 정지작업이다**(사용자 지적, 2026-07-29). 작업대 우 pane 은
**이미 렌더러**다 — 「채운 모습 / 원문」 토글 + 대상 글꼴 선언 + 정렬 린트(`wbLint`)가 "붙여넣을
곳에서 어떻게 보이는가"를 그린다. HWPX 미리보기가 필드×값 표인 유일한 이유는
`screen_job.py:1029`·`job.js:456` 이 못 박은 전제 *"hwpx 본문은 앱에서 렌더 못 한다"* 하나이고,
그 전제가 뒤집히면 **두 pane 은 구분되지 않는다**. 부속은 이미 같은 자리에 같은 것이 붙어 있다
(레코드 이동 `wbPosition`↔`previewPos`, 곁줄 `wbLint`↔`previewEvidence`, 산출 표지
`wbReview`↔`previewFilename`).

수렴에 **포함되지 않는 것 둘**(렌더러가 와도 안 없어진다):

- **집합축은 배치 도구의 성질이다.** HWPX 는 N건을 한 번에 만들어 접힌 뷰와 ack 게이트가 계속
  필요하다. 그래서 최종 형상은 「작업대와 같은 화면」이 아니라 **작업대 우 pane + 집합 pane**
- **작업대의 렌더는 산출물 그 자체**(붙여넣으면 그 텍스트)인데 **HWPX 의 렌더는 산출물의
  그림**이다. 그래서 HWPX 쪽에는 파일 이름·저장 경로가 pane 에 반드시 붙고 작업대엔 그 축이 없다

**렌더러 슬라이스가 함께 지는 의무**: 부분 충실도 렌더는 **조용히 틀린 그림**이다. 텍스트 렌더는
글꼴 폭 문제를 린트로 정직하게 말할 수 있지만, HWPX 레이아웃을 근사로 그리면 "봤는데 다르게
나왔다"가 성립한다 — 근사·실패 구간을 시끄럽게 표시하는 몫이 렌더러에 붙는다.

**순서**: §2.1 회귀 복구와 §2.2~2.4 착지 **뒤**다. §5.2 의 splitter 항목도 회귀 복구 후 재평가를
조건으로 달고 있고, 두 결정이 같은 면의 기준면을 건드린다. 지금 안 지으면 렌더러 슬라이스가
표면 재편까지 떠안는다는 것이 이 항목을 살려 두는 이유다.

**계약 비용**(착수 시): `#previewModal` id 소멸 → 정적 DOM 계약 **선행** 갱신,
`preview_move`·`preview_approve` 는 액션 유지·소비 표면만 교체, selftest 프로브 재작성,
`UI_CONTRACT.md` 화면별 계약 갱신. 곁들여 우 pane 을 **공용 「레코드 pane」 계약**으로 세울지
결정한다 — 지금은 `.wb-preview`(`tail.css`)와 드로어가 CSS·DOM 이 남남인데, 같은 것이 될
물건이라면 형상을 미리 맞추는 편이 싸다.
