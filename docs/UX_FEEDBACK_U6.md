# U6 실사용 피드백 라운드 — 작업 조합 재편 판정 기록

> **문서 상태:** 유효 결정 (착수 2026-09-02 · 완주 2026-09-03)
> **권위 범위:** 작업 생성·편집 흐름의 재편 판정과 그 근거, 사용자 확정 사항
> **조치 추적:** 우산 #974 · 슬라이스 #975~#980 → PR #983~#990 · 회수 #984·#986·#991
> **동결 시안:** `docs/u6-mockups/pairing-flow.html`

2026-09-02. 사용자 문제 제기 한 건에서 출발한 라운드다: 「템플릿과 데이터가 1:1 강결합인데
작업 생성·편집은 정보가 파편화되어 쏟아진다. 워크플로는 **템플릿과 데이터를 매칭 → 매핑·
표시형 확인 → 작업명·파일명 정하고 저장** 으로 끝나야 한다. 블록·다이어그램 기반의 세련된
경험을 원한다. 템플릿을 끌어와 복사해 관리하는 체계 대신 폴더를 지정해 일괄 등록하고 싶다.
데이터 풀은 이미 풀처럼 기능하는데 문서 만들기의 데이터 선택에서만 닿는다.」

U5 가 **표면 감량**이었다면 U6 는 **표면 재배치**다. 걷는 것보다 옮기는 것이 많고, 옮기는
기준은 하나다 — 각 단계가 **하나의 질문**만 하게 한다. 원칙의 갱신은 없다. 「조용히 틀리지
않는다」와 「같은 상태를 두 곳이 판정하지 않는다」가 이 라운드의 모든 판정을 가른다.

## 1. 근거 — 코드 조사 1 + 웹 리서치 2

**코드.** 편집기는 `template → binding → filename` 세 탭이고 저장 게이트(`gui/job_editor_state.py`)
도 그 순서로 고정돼 있다. 즉 목표 워크플로와 **형태가 같다**. 파편화의 원인은 단계 수가
아니라 각 탭에 얹힌 것들이다:

| 탭 | 안에 있는 것 | 작업 만들기에 필요한가 |
|---|---|---|
| 템플릿 | 가져오기 3버튼 · HWPX/TXT 밴드 · 구간 항목 표(행 동사 3 + 밴드 동사 1) · 선택 chip + 경로 동사 · 출처 · 스키마 표 · 구간 요약 | **고르기만.** 나머지는 템플릿 *관리*다 — 구 `tpl` 화면이 F8 에서 죽으며 여기로 흘러들었다 |
| 필드 연결·표시 | 데이터 관문 · 축약 풀 목록 · 헤더 행 · 사용할 열 칩 · **7열** 매핑표 · 레코드 스테퍼 · 카운트 3종 | **절반.** 데이터 고르기는 1단계로, 표는 4열로 |
| 파일 이름 | 패턴 + 표본 미리보기 | 그대로. 작업 이름이 합류한다 |

`screens/editor.ts` 2,089줄, `screen_editor.py` 2,574줄 — 프런트·컨트롤러 모두 최대 파일이고
둘 다 「템플릿 관리」와 「작업 정의」 두 책임을 진다. 템플릿 쪽은 「폴더가 곧 풀」
(`~/.hwpxfiller/templates` 재귀 나열)이지만 가져오기가 앱 홈으로 **복사**하고 원본 링크를
남기지 않는다(`external/template_files.copy_into_library`). 데이터 풀은 durable 레지스트리 +
5 관리 동사 + 손상 격리를 가진 1급 개체인데 표면은 「데이터 선택」 다이얼로그 하나이고,
편집기에는 축약판 `PoolPickList` 가 따로 서 있다 — 같은 상태를 두 표면이 다르게 그린다.

**문서 템플릿 × 스프레드시트 제품군**(Word 편지 병합, Autocrat·YAMM·Document Studio·Form
Publisher, Documint·Docupilot·Formstack·PandaDoc, Carbone·Docmosis·Plumsail·Windward, Airtable
Page Designer, Webflow·Framer CMS, Figma Sheets Sync). 선을 그어 잇는 UI 는 **한 곳도 없다.**
지배 패턴은 「이름이 같으면 자동, 안 맞는 것만 사람이 본다」. 매핑 화면이 곧 미리보기인
제품(Airtable·Webflow·Framer)이 만족도가 높고, 미리보기를 뒤 단계로 뗀 제품(Word·YAMM·
Formstack)에 「다 하고 나서야 틀린 걸 안다」는 불만이 몰린다. 반복 실패 셋 — 이름 한 글자
불일치의 조용한 빈칸, 소스 갱신 뒤 재매핑 누락, 눈에 안 띄는 바인딩 진입점 — 은 전부 이
저장소의 원칙이 이미 막는 결함류다. 표시형 UI 는 업계 전반이 결손(Word 는 `\@` 스위치, SaaS
는 토큰 함수)이라 우리의 타입 파생 표시형 select 는 감량하되 잃지 않는다.

**통합·ETL 도구**(MapForce, Talend, Boomi, Informatica, DataWeave, SnapLogic, ADF, Fivetran,
Zapier, Make, n8n, Power Automate, Salesforce·HubSpot import). 선 캔버스를 쓰는 곳(MapForce·
DataWeave)은 **트리형 XML** 이 대상이다. 평면 열 목록을 다루는 도구는 예외 없이 2열 표 +
자동 매칭 + 예외 편집으로 수렴했고, 자동·수동·미매핑을 **상태로 구분**해 보인다(Informatica
「Undo Automap」, Salesforce 미매핑 별도 열거). n8n 은 드래그가 만든 표현식의 잘못된 참조
결함이 다수 보고됐다 — 드래그는 가속기이지 유일한 경로가 아니어야 한다.

**폴더 = 라이브러리 관례**(Word 「기본 개인 서식 파일 위치」, 한글 문서마당, Obsidian, Zotero,
Lightroom, Ableton, Calibre, VS Code, Blender Asset Library, Unity `.meta`, Unreal Import,
Plex/Jellyfin). 폴더 밖 파일은 복사로 강제(Unreal·Calibre), 사라진 파일은 즉시·구체적으로
알림(Zotero — 반면교사 Plex 의 조용한 빈 목록), 파생물은 원본 옆 사이드카(Unity·Blender),
읽는 시점은 「열 때 diff + 수동 새로 읽기」(Word·Unity·문서마당 — 상시 감시는 Obsidian 뿐).

## 2. 판정

### 2.1 필드 수준 「선 긋기」 캔버스는 기각한다 — 다이어그램은 조합 수준에서 산다

근거는 §1 그대로다. 「블록·다이어그램」 감각이 사는 자리는 **템플릿 블록 하나 + 데이터
블록 하나 + 연결 카드 하나 = 작업** 이다. 1단계가 그 그림이고, 연결 카드의 수치(「필드 12 ·
열 18 · 자동 연결 10 · 확인 필요 2」)는 링1 이 지금 이미 계산하는 자동 제안 결과다. 필드
수준은 2열 표다.

### 2.2 세 단계는 유지하고, 각 단계가 하나의 질문만 한다

- **1 고르기** — 「어느 템플릿을 어느 데이터에?」 좌 템플릿 풀 · 중앙 연결 카드 · 우 데이터 풀.
  시트·헤더 행은 데이터 항목이 이미 든 정체성 축(U4 §2.4)이라 다시 묻지 않는다. 파일
  찾아보기로 새로 연 다중 시트만 시트 확정 게이트. 클릭 선택이 1차 경로, 끌어 놓기는 같은
  액션을 발행하는 가속기.
- **2 연결 확인** — 「이 연결이 맞나?」 7열 → 4열(템플릿 필드 · 데이터 열[제안/확인/확인 필요
  배지] · 표시형 · 실제 행 미리보기). 「타입/고정값」은 데이터 열 select 의 마지막 항목군
  (고정값…, 오늘 날짜)으로, 「상태」는 미리보기 셀의 표식(`〘미입력·…〙`)으로 흡수. 행별
  「확정」 체크는 상태 배지 + 「제안 n건 모두 확인」 일괄 승격으로 — 확인 필요 항목은 그
  버튼이 건드리지 않는다. **명시성 게이트는 그대로다.** 「제안 → 확인」 전이는 여전히 사람이
  만들고, F-06 의 규칙 지문 두 축(`source`/`format`)과 `reviewed_rules` 의미는 불변이다.
- **3 이름·저장** — 「뭐라고 부르고 뭐라고 저장하나?」 작업 이름(기본값 「{템플릿} — {데이터}」
  도출) + 파일 이름 패턴 + 저장 폴더 병기(읽기 전용, #968 전역 값). 「저장하고 문서 만들기로」.

### 2.3 템플릿 풀은 폴더 등록이다 — 단일 루트, 재귀, 제자리 변환

「폴더가 풀」 구조는 이미 서 있고 빠진 것은 그 폴더를 사용자가 고르는 것뿐이다. 설정 모달에
「서식 폴더」 행을 더하고, 지정이 없으면 지금의 앱 홈 템플릿 폴더가 루트다 — 기존 사용자는
아무것도 잃지 않고 이행 비용은 0 이다.

| 규칙 | 판정 |
|---|---|
| 루트 | **하나**(사용자 확정). 다중 폴더 사례(Blender·Ableton)는 채택하지 않는다. `library_key` 는 루트 상대 경로로 뜻이 그대로 이어진다 |
| 하위 폴더 | **재귀**(사용자 확정). `.hwpx`·`.txt` 둘 다. 하위 폴더는 정리 축이지 상태 축이 아니다 — 목록에 상대 경로만 병기, 접기 없음 |
| 읽는 시점 | 화면 진입 시 diff + 「새로 읽기」. 상시 감시 없음 |
| 폴더 밖 파일 | 「파일 가져오기…」= 루트(또는 고른 하위 폴더)로 **복사**. 임시로 여는 세 번째 길은 만들지 않는다 |
| 사라진 파일 | 목록에서 지우지 않고 비활성 + 「경로를 찾을 수 없음」. 데이터 풀 「끊김」과 같은 문법 |
| 삭제·휴지통 | 사용자 폴더에 `.trash` 를 만들지 않는다. 앱은 읽기만 하고 쓰는 것은 제자리 변환 하나. 「폴더에서 보기」가 삭제 동사를 대신 |
| 변환 | **제자리 멱등 변환 유지**(§2.8 재판정). 파일 하나가 항목 하나, 상태(RAW·PARTIAL·COMPILED)는 매번 재계산(`domain/template_status.py`). 「누름틀·구간 변환」은 같은 파일을 덮어쓰고 이미 변환된 파일에는 no-op. 변환 전 항목은 비활성 + 사유 |

PARTIAL 게이트(#835 D5)와 상태 재계산(`domain/template_status.py`)은 건드리지 않는다.
배포는 변환된 파일만 하므로 대다수 사용자의 풀에는 「변환 필요」 항목이 서지 않는다. 변환 전
항목이 있으면 숨기지 않고 비활성 + 사유(「변환 필요 · 표기 n건」)로 선다.

### 2.4 데이터 풀은 고르기 화면의 오른쪽 열 그 자체다

「데이터 선택」 다이얼로그와 **같은** `PoolController` 구독·같은 컴포넌트를 두 자리에 세운다.
고정·보관·활성화·다시 연결·삭제·파일 찾아보기·계약 목록 등록이 전부 거기 있다. 문서 만들기
에서 데이터를 먼저 여는 흐름(데이터 → 결속된 작업 후보)은 U4 §2.4 의 축이라 그대로다.
편집기 축약판 `PoolPickList` 는 소비자 0 이 되는 순간 사슬째 퇴역한다(R5-99 B2 선례).

### 2.5 「사용할 데이터 열」 선별은 퇴역한다 (사용자 확정)

스키마를 재활용한다는 가정 아래 불필요한 스키마를 정제하려던 물건이고 그 전제는 더 없다.
매핑되지 않은 열은 자연히 쓰이지 않으며, 표 바닥의 「안 쓰는 열 n개」 한 줄이 그 정보를
잇는다. 링1 의 열 선별 상태·액션·payload 는 소비자 0 확인 후 함께 걷는다.

### 2.6 「문서 작업」 상세 패널의 빈 하단은 같은 연결 그림이 채운다 (사용자 추가 제안)

오른쪽 `library-detail` 은 화면 전체 높이인데 내용은 이름·방식·사실 3행뿐이다. U5 #966 이
실행 이력과 「필드 연결」 섹션을 걷은 이유는 **소비자 0 인 별도 payload 사슬**이었지 정보
자체가 아니었다. 그래서 편집기 1·2단계가 쓰는 **같은 링1 투영**을 읽기 전용으로 한 번 더
세운다 — 연결 카드 + 4열 표(필드 · 데이터 열 · 표시형 · 첫 행) + 바닥 한 줄(파일 이름 계획 ·
저장 폴더). 「첫 행」은 데이터 파일을 읽어야 하므로 선택 직후 「—」, 읽기가 끝나면 채우고,
끊김이면 그 자리에 사유(조용한 빈칸 금지). 동사는 늘지 않는다 — 재선택 버튼은 #966
deep-link 그대로이고 행 클릭이 같은 배관으로 2단계에 착지한다. 패널을 접어 목록을 넓히는
대안은 증상만 가리는 것이라 기각했다.

### 2.7 끌어 놓기 조합은 1차에 넣는다 (사용자 확정)

항목을 상대 열의 선택 항목 위에 놓는 HTML 드래그라 비용이 작다. 클릭과 같은 액션을
발행하므로 헤드리스 테스트는 두 경로가 같은 상태를 만드는지만 본다.

### 2.8 컴파일 산출물 분리(`.tpl` 사이드카)는 철회한다 — 제자리 멱등 변환이 옳다 (사용자 재판정)

첫 확정 ②는 컴파일본을 원본 옆 `X.tpl.hwpx` 로 두는 것이었다. 되짚은 결과 그 모델은 「변환 전
원본」을 풀의 **영구 거주자**로 만든다 — 실행할 수 없는 파일이 「변환 필요」 상태로 계속 남고,
배포받은 사용자의 폴더에는 없는 파일이 저작자 폴더에는 항상 하나 더 있다. 두 파일의 존재·
수정 시각에서 항목 상태를 합성하는 규칙(원본이 더 새것 · 둘 다 있음 · 컴파일본만)과 접미사
없는 기존 변환 파일의 승격 이행도 전부 그 위에 얹힌다. 현행 제자리 변환은 **파일 하나 = 항목
하나**이고 상태는 파일 자신에서 계산되므로 그 축이 통째로 사라진다. 변환은 같은 파일을
덮어쓰고 이미 변환된 파일에 다시 걸면 「바꿀 것 없음」 no-op 이다(멱등). 재저작 동선은 U4
§2.16 이 이미 세운 「전부 표기로 되돌리기(제자리) → 한글 편집 → 다시 변환」이 그대로 진다.
확정 ②는 이 판정으로 대체된다.

### 2.9 U4 §2.15·§2.16 의 승계 — 구간 요약·일괄 되돌리기는 항목 상세 시트로 (U6-E)

**무엇이 옮겨졌나.** 편집기 고르기 존 **아래**에 남아 있던 템플릿 관리 표면(선택 chip +
경로 동사 · 스키마 표 · 구간 항목 밴드 `#tplSlots` · 구간 요약 `#editorSlotSummary`)이 좌 열
항목의 `⋯` 메뉴 + **항목 상세 시트**(`#tplDetailModal`) 하나로 모였다. 1단계가 묻는 질문은
「어느 템플릿을 어느 데이터에?」 하나이고, 저것들은 전부 **그 답 뒤에 묻는 다른 질문**
(「그 항목이 지금 어떤가」)이라 같은 자리에 있을 이유가 없었다.

**「작성 출처」 블록은 옮긴 것이 아니라 걷은 것이다**(#989 리뷰 6 정정). 그 블록이 그리던
네 줄(템플릿·데이터·필드 지문·데이터 열)은 저장된 mapping 이 이미 든 durable 기록의 재진술
이었고 표면 소비자가 0 이 됐다. 다만 그 블록이 **하나를 더 이고 있었다** — 「작성 당시와
템플릿 필드 구성이 다릅니다」 경고다. 그건 풀 항목의 사실이 아니라 **세션 판정**이라(저장이
찍은 필드 지문 ↔ 지금 연 파일의 필드) 시트가 아니라 1단계 게이트 존에 산다. 판정도 문안도
Python 이 낸다(`_provenance_drift` → 스냅샷 `schema_drift`) — 웹이 필드 목록을 다시 대조하면
같은 사실을 두 층이 판정한다.

**U4 §2.15 의 판정은 폐기가 아니라 승계다.** 그 절이 편집기 구간 존을 **읽기 전용**으로 둔
근거는 「저장 전 초안은 템플릿 파일을 변이시키지 않는다」였다 — 즉 **동사 부재** 판정이었고,
그것이 tpl 검토의 같은 모양 목록(동사 3종)과 갈리는 유일한 축이었다. U6-E 에서 그 축이
움직인다: 동사는 편집 세션이 아니라 **풀 항목(파일)** 을 겨누는 시트에 서고, 시트는 세션과
무관하게 어떤 항목에서도 열린다. 마침 세션이 든 파일이면 기존 seam(`mutation_sinks` →
`reconcile_template_mutation`)이 스키마 무효화와 notice 를 그대로 진다 — 그 사슬은 이 라운드가
손대지 않았고, 「초안이 자기 템플릿을 조용히 바꾼다」는 결함류도 그 자리에서 계속 막힌다.
근거가 옮겨졌으므로 존도 옮긴다: 값의 모양(`SlotView.to_dict`)은 그대로 하나이고, 사라진 것은
**같은 목록을 두 자리에 그리던 사본**이다.

**U4 §2.16 의 「편집기 쪽은 불변이다」 한 줄은 이 판정으로 갱신된다.** 밴드 동사
(`slot-decompile-all`)의 노출 술어·확인 문안·대상(파일 하나)은 전부 불변이고, 바뀐 것은 그
표가 서는 자리다.

**도달성 구멍이 함께 메워졌다.** U6-B 가 링1 목록에서 `preview`·`make_job` 을 걷으며 COMPILED·
FILLED 행의 동사가 0 이 됐는데, 구간 항목 동사(개명·표기로 되돌리기·삭제)는 **정확히 그 두
상태에서만** 존재한다 — 변환이 끝난 파일에만 native Slot 이 있기 때문이다. 즉 그 동사들에 닿을
길이 그 순간 0 이 됐다. `_STATE_ACTIONS` 의 COMPILED·FILLED 에 `review` 를 세워 그 구멍을
메운다: `review` 는 읽기 전용이고 이제 시트의 재료를 채우므로 어느 상태에서든 물을 수 있다.

**「자세히…」는 모든 행에 선다.** 그래서 동사 0 인 행이 없고, U6-A 가 세운 「동사 0 → `⋮`
비활성 + 사유」는 근거와 함께 걷혔다(`LIB_ROW_NO_ACTION_REASON` 삭제). 그 판정이 막던 것은
**무반응 버튼**이었고 그 금지는 그대로다 — 어느 행이든 누르면 답할 것이 있고, 판독 실패 행에서
`⋯` 가 여는 것은 그 사유를 보이는 시트다.

**편집기가 tpl 과 별개로 들던 중복도 함께 접혔다.** 종전에는 편집기가 자기 hwpx VM 과 자기 TXT
레지스트리를 들고(앱 조립에서 같은 인스턴스를 주입해 「단일 실체」를 지켰다) 라이브러리 소속을
**다시 판정**했다. 이제 넘기는 것은 판정 하나다(`TemplateController.is_live_path` — 편집기는
상대의 형체를 모른다). 같은 질문에 답하는 스캔이 하나가 됐고, hwpx 는 판정 전에 재스캔하므로
「방금 사라진 파일」의 처리도 매체마다 갈리지 않는다.

  「자세히…」 하나가 진다(같은 왕복을 부르는 메뉴 항목을 둘 두면 사람이 그 차이를 물어야

  §2.9 정정). ③ **시트가 열려 있는 동안의 결과·실패는 그 면 안**에 선다 — 스크림이 화면을
  덮는 자리에서 좌 열 바닥 줄과 `#save-msg` 는 읽는 사람에게 닿지 않는다.

  새지 않게 하고(`BadZipFile` 은 `ValueError` 가 아니다), 파일을 바꾼 **모든** tpl 동사가
  열려 있는 상세를 재투영하며, 부재로 확정된 경로는 거절 **전에** 갱신된 목록을 밀고, 서식
  폴더 밖 템플릿의 시트 문은 비활성 + 사유이며, 관문은 캐시 적중에서 재스캔하지 않고 검토는
  파일을 한 번만 연다.

  카드 + 읽기 전용 4열 표 + 계획 한 줄**로 찼고, 그 표의 행은 편집기 2단계와 **같은 링1 순수
  함수**(`gui/mapping_state.row_projection`)가 낸다 — 편집기의 `_row_snapshot` 은 그 얇은
  래퍼가 됐다. #966 이 걷은 것은 정보가 아니라 별도 라벨 사전을 든 payload 사슬이었으므로,
  되살리는 길은 **투영과 라벨을 링1 로 올려 두 호스트가 같은 값을 소비하는 것**이었다(옛 키
  `bindings` 는 되살리지 않는다 — 이름이 `pairing_detail` 인 이유). 새 액션은 0 이고 동사도
  늘지 않았다: 재선택 두 버튼은 #966 deep-link 그대로 자리만 옮겼고, 행 클릭은 기존
  `target: binding/<필드>` 문맥을 프런트에서 **처음** 소비한다.
  판정이 함께 선 것 셋: ① 「첫 행」은 명시 3태(`pending`/`ready`/`error`)이고 `record={}` 로
  미읽음을 흉내 내지 않는다 — 빈 레코드는 미입력 표식을 찍어 「산출물이 담을 것」과 「아직
  모름」을 한 글자로 접는다. ② 지연 읽기는 컨트롤러의 사적 캐시 + 워커 + **상관 키 대조 뒤
  전체 스냅샷 재푸시**이고, 「선택 ≠ 착석」 불변은 그대로다(다른 화면의 마운트 경로를 재사용
  하지 않는다). ③ 카드의 「확인 필요 k」는 저장된 프로파일에서 셀 수 없다(확정 행만 담는다)
  — 재료는 매 refresh 이미 도는 `TemplateStructureDrift` 이고, 그래서 수치가 링1 `JobRow` 로
  올라왔다. 좌:우 비율도 `1fr : 1.25fr` 로 뒤집혔다.
- U6-F 의 리뷰 회수(#990 · 10건)가 같은 슬라이스에 착지했다. 판정이 바뀐 것 셋:
  ① **표의 행은 저장본이 아니라 템플릿에서 선다** — 프로파일로 세우면 표가 카드와 다른 필드
  집합을 말한다(미커버 필드는 행이 없고, 사라진 옛 연결은 템플릿 필드인 척 선다). 미커버는
  `needs_source` 행으로, 소멸분은 표 밖에서 이름으로. 템플릿을 못 읽는 갈래는 저장본으로
  그리되 **그 사실을 명시**한다. ② **「세었는가」는 수치가 아니라 명시 boolean 이 답한다**
  (`TemplateStructureDrift.readable`) — 읽기 실패 갈래의 대칭차는 전부 비어 있어 「차이 없음」과
  한 모양이고, 그 위의 카드는 「연결 n / n · 확인 필요 0」을 지어냈다. 필드 0 개인 읽을 수
  있는 템플릿은 `연결 0 / 0` 을 말한다. ③ **읽기 시작 판정은 스냅샷 산출 한 자리**다 —
  핸들러마다 걸면 상태를 바꾸는 경로가 늘 때 그 자리를 하나씩 더 기억해야 하고, 실제로
  다시 연결·복원·복제 셋이 빠져 상세가 「아직 모름」에 머물렀다. 그 대가(중복 기동)는 진행 중
  키 집합이 진다.
  나머지 일곱은 같은 원칙의 집행이다: 캐시 키에 **파일 지문**을 넣어 낡음을 구조적으로 막고,
  실패는 캐시에 남기되 명시 선택이 걷으며, 참조 끊김 판정은 단일 출처를 지나고, 미리보기 칸
  렌더러를 **하나**로 합치고(닫힌 집합이 이미 갈려 있었다), 존을 재료 전부를 덮는 키로 memo
  하고, 자르기를 투영보다 **먼저** 하고, 매체 재판정 대신 링1 이 실어 보낸 값을 쓴다.
- **상세 패널 마감 재판정**(2026-09-03 · 사용자 실사용). 다섯이 바뀌었다. ① 「그 밖에 n행: 이름…」
  나열이 **퇴역**하고 표 밖 건수 한 줄(「필드 N개 중 n개」)이 그 자리에 선다 — 좁은 상세에서 그
  목록이 표만큼 길어져 정작 표를 밀어냈다. 페이로드 `more_fields` 는 이름을 그대로 싣고 링2 가
  길이만 읽으므로 되살릴 때 그 자리에서 다시 소비하면 된다(감추는 것이 아니라 세는 것이다).
  ② 동결 시안 장면 4 의 **음영 위계가 복원**됐다 — 패널·카드·항목 3층 면, 항목과 재선택 버튼의
  가로 한 줄(두 축 버튼이 같은 열에 선다), primary 색 연결선, 채운 표 머리. 빈 사각형 아이콘은
  정체를 말하는 글리프(문서장 / 표)로 바뀌었다. ③ **계획 줄은 라벨 한 행**(파일 이름 + 나머지
  건수)이다 — 한 문장에 가운뎃점으로 이으면 어느 값이 무엇의 답인지가 읽는 사람 몫이 된다.
  행 클릭 안내 문장은 행마다 `title` 이 이미 지므로 **걷혔다**. ④ **저장 폴더는 상세에서
  퇴역**했다(사용자 확정) — U5 에서 전역 단일 값으로 올려 설정 창이 소유하는 축이라, 작업
  상세의 재진술은 소유자를 둘로 보이게 했고 그 자리의 열기 동사도 실사용에서 동작하지 않았다.
  링2 `pairing_detail` 의 `output_folder` 존과 `remembered_output_directory` 주입이 소비자 0 으로
  함께 사라졌다(시안 장면 4 의 바닥 줄 「저장 폴더」는 이 판정이 대체한다 — 동결 파일은 불변).
  ⑤ **「템플릿 재선택」·「데이터 재선택」 두 버튼이 가운데 「연결」 손잡이 하나로 접혔다**
  (사용자 재판정). 두 버튼은 대칭인 듯 보였지만 착지가 달랐다 — 데이터 재선택은 편집기 필드
  연결 단계라 「작업 편집」 기본 착지·표 행 클릭과 같은 자리였고(완전 중복), 템플릿 교체는
  매핑까지 가는 정체 교체라 부류가 다르다. 그래서 두 항목 사이의 관계를 그린 줄(연결선 + 수치)
  이 버튼이 되어 필드 연결 단계로 들어가고, 템플릿 교체는 「작업 편집」 → 템플릿 탭이 진다.
  차단 해소 동사(미결속 「데이터 연결하기…」·부재 「다시 연결」)만 항목 곁에 남는다. §2.6 의
  「동사는 늘지 않는다」 가 한 단계 더 줄었다.
