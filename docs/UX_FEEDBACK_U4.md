# U4 실사용 피드백 라운드 — 트리아지와 판정

접수 2026-08-29. v0.5.0(`a9c78bc`) 출하 직후 받은 실사용 피드백 34항이다. 앞선 두 라운드와
다른 점은 **이미 착지·문서화된 판정을 정면으로 뒤집는 항목**과 **단순 표면 감량**이 한
덩어리로 섞여 있다는 것이다. 성격이 다른 것을 한 라운드로 묶으면 뒤집기가 감량을 인질로
잡으므로, 우산 이슈 **#932** 가 34항의 트리아지·충돌 지점·라운드 분할을 지고 이 문서는
**판정**을 진다. 슬라이스 번호 정본은 #932 의 KICKOFF 코멘트다.

라운드 분할(#932 §3): **A** 결함 수리 · **B** 표면 감량 · **C** 데이터 모델 재판정 ·
**D** 그리드 재설계 · **E** 신규 기능 · **F** 튜토리얼 리서치. C·D 는 둘 다
`screen_job.py`·`data_zone.ts` 를 겨누므로 **병렬 금지**(직렬).

## 1. 착지한 판정 — U4-A(결함 수리)

여섯 건 전부 「존재하지 않는 결함」이 아니었다. 코드 좌표로 원인이 확정된 것만 여기 싣는다.

게이트는 방어층으로 남는다: 앱 밖에서 편집된 작업은 여전히 미해소 토큰을 들 수 있다.

## 2. 재판정 기록 — 뒤집은 것

### 2.1 승인 뒤 확인 면은 **닫힌다** (21번)

뒤집는 판정: `docs/archive/DATA_FIRST_INTEGRATION_MAP.md:1472` — *"승인은 … 면이 열린 채
상태만 갱신한다(닫지 않는다 — 승인 후 나머지 레코드를 계속 넘겨볼 수 있어야 한다)"*, 검증란은
「실앱 게이트: 승인 뒤 면 생존」.

**판정** 그 계약은 stale 하다. 승인은 「이미 확인했다」는 뜻이므로 확인하라고 띄운 면을 그
자리에 세워 둘 이유가 없다 — 더 볼 것이 있으면 **다시 여는 것**이 그 동사다. 거절은 반대로
면을 남긴다: 무엇이 왜 안 됐는지 말할 자리가 거기다. 승계 진술은 `docs/UI_CONTRACT.md` 의
확인 면 절이 지고, 동결 문서는 고치지 않는다(#932 B1 의 처리 방식).

### 2.2 이름 충돌은 **blocker 가 아니다** — 기본 덮어쓰기 (27·28번)

뒤집는 판정: `DEFAULT_COLLISION_POLICY = "ADD_SUFFIX"` 와 그 짝 계약
*"덮어쓰기는 사용자가 명시로 골라야 한다"*. #932 §0 의 1차 확정(「UI만 감량, 기본값은
ADD_SUFFIX 유지」)도 이 판정이 대체한다(사용자 확정 2026-08-29).

**사실 정정 둘.** ⑴ `DESTRUCTIVE_OVERWRITE` 승인은 **매 실행이 아니라 실제로 덮어쓸 항목이
있을 때만** 선다(`preview_requirement.py` 는 item 의 `collision_disposition` 을 본다) — #932
§2 B2 의 「매 실행마다 승인 왕복 강제」는 과장이었다. ⑵ 이름 충돌이 blocker 로 서는 것은
`FAIL` 정책에서뿐이고, 일반 생성 경로는 애초에 `collision_policy` 를 보지 않는다
(`plan_generation` → `needs_overwrite` → 충돌 파일 이름을 세어 모달로 알린 뒤 진행). 즉
선택기는 **실제로 도는 경로를 지배하지도 않으면서** 서 있었고, 그래서 두 경로가 같은 상황을
다르게 말했다.

**판정** 같은 이름이 있으면 덮어쓴다(기본값 `OVERWRITE_EXPLICIT`). 조용히 덮지는 않는다 —
덮어쓸 항목이 하나라도 서면 확인 면이 `DESTRUCTIVE_OVERWRITE` 로 REQUIRED 가 되고, 무엇을
덮어쓰는지는 「생성 예정 문서」 목록이 **파일마다** 말한다. 「충돌 처리」 선택기(27)와 「목록
새로 확인」(28)은 화면에서 걷혔고 그 두 액션도 registry 에서 사라졌다.

「조용히 덮지 않는다」를 지키던 것이 `DEFAULT_COLLISION_POLICY != OVERWRITE_EXPLICIT` 라는
**규칙의 존재**였다는 점이 이 라운드의 교훈이다. 그 자리는 이제 **결과**가 진다 —
`tests/test_preview_requirement.py` 의 「의도가 아니라 실제 처분이 승인을 세운다」가 그것이고,
`is_destructive` 는 승인 판정의 입력이 아니다(기본값이 된 뒤로 거의 언제나 참이라 정보가 0).

application 층은 정책 셋을 계속 지원한다(어댑터·계약 테스트가 그 축을 진다). 걷힌 것은
**제품 표면의 선택**이다.

### 2.3 `REVIEW_DELIVERY` 어포던스 재선언 (#912 3층 계약)

`#jobRefreshDelivery` 가 사라지면 이 blocker 의 복구 동사가 비므로 — #912 가 이름 붙인 결함류를
우리 손으로 만드는 꼴이라 — 좌표를 함께 재선언했다: `ACTIVE_VERB → #jobManagedPickFolder`
(직접 브리지 `pick_output_folder`). 근거는 남는 원인이 갈린 것이다. 이름 충돌 갈래가 사라진 뒤
이 자리에 서는 것은 ⑴ 덮어쓸 수 **없는** 물건(같은 이름의 폴더·바로가기)에 이름이 걸린 경우 —
저장 폴더를 바꾸면 지워진다 — 와 ⑵ 파일 이름 규칙 자체의 미해소인데, 후자는 4번의 저장 시점
게이트가 앱 안에서 만들어지는 것을 막고 앱 밖 편집분은 `#jobDeliveryBlockers` 가 사유를 병기한다.
종전 좌표의 「목록 새로 확인」은 충돌 갈래에서만 참이었고 나머지 원인에는 아무 일도 하지 않았다.

### 2.4 작업↔데이터는 **durable 강결합**이다 — 판정 D 폐기 (1·2·3번, U4-C)

뒤집는 판정: `docs/UX_FEEDBACK_U2.md` §5.3 **판정 D**(#347 → #362 `27f7b0a`, 파괴적) —
*"작업↔데이터 결속(`default_dataset_ref`, #53-A)을 폐기한다"*, 그리고 같은 절의 뒷문 금지
조항 *"「이 데이터로 자주 쓰는 작업」류의 데이터별 선호를 나중에 만들면 그것이 곧
`default_dataset_ref` 의 재발명이다. 데이터↔작업 결속은 **어느 방향으로도 다시 들이지
않는다**"*. **그 문장을 명시로 철회한다**(사용자 확정 2026-08-29).

**전제 정정 — 사용자가 말한 「스키마 재활용」은 구현된 적이 없다.** 스키마 호환 판정 함수는
저장소에 미발견이고 오히려 반대가 명시 구현돼 있었다: `_model_key_now()` 가 `data_path` 를
정체 성분으로 들어 **헤더가 같아도 데이터 경로가 바뀌면 전 행이 미확정으로 강등**된다
(`screen_editor.py`). 과중한 복잡도의 출처는 재활용 지원이 아니라 **결속 부재**다 — `Job` 에
데이터 필드가 없어 「데이터 없이 작업 만들기」가 예외가 아니라 **유일한 경로**이고, 그래서 매
세션 데이터를 다시 고른다. 1·2·3 은 별개 항목이 아니라 **한 뒤집기의 세 얼굴**이다.

**판정 D 가 실제로 무너진 지점은 결속이 아니라 결속의 키였다.** 그 필드는 **풀 항목 이름**을
들었는데, 같은 절의 **판정 C** 가 바로 그 이름을 「중복 허용·개명 자유의 순수 라벨」로 강등해
정체성을 경로+시트로 옮겼다. 이름을 외래참조로 든 유일한 소비자가 `default_dataset_ref` 였고,
그래서 이름 정체성 문제가 거기서만 터졌다. 판정 D 는 그 증상을 결속 자체의 죄로 읽었다 —
**되들이는 결속의 재료는 판정 C 가 확정한 정체성 축**이고, 이름 축은 부활하지 않는다.

#### 모델 — 관계는 하나다

```
Job.data_path / data_sheet / data_header_row   ← 유일한 작업↔데이터 관계
        │                                   ▲
        │ 작업 선택 → 결속 데이터 마운트      │ 편집기 저장만 쓴다
        ▼                                   │
   마운트된 데이터 ──── 역인덱스 ────→ 이 데이터에 결속된 작업(후보)
```

| 축 | 판정 |
|---|---|
| 강도 | **필수** — 빈 결속은 「데이터 연결 필요」 상태이고 편집기 저장 게이트가 요구한다. 그 상태의 생산자는 구판 파일과 앱 밖 편집분뿐이다 |
| 방향 | **병존 폐기** — 스키마 호환 후보와 결속을 동시에 세우지 않는다. 데이터→작업은 같은 결속의 **역인덱스**이지 두 번째 기제가 아니다 |
| 재료 | 마운트 시점에 한 벌로 포획한 `path`·`sheet`·`header_row`. 풀 슬롯 키가 아니다 — 슬롯은 「다시 연결」로 내용물이 갈리는 가변 개체라(#347) 작업이 그것을 들면 표시는 A·시작은 B 가 된다 |
| 쓰기 동사 | **편집기 저장 하나.** 월별로 파일이 갈리는 사람도 「데이터 바꾸기 → 저장」 두 걸음을 지난다 — 결속을 바꾸는 것은 규칙을 바꾸는 일이다 |
| 후보 축 | **결속 역인덱스만.** 새 데이터를 처음 마운트하면 후보 0건이 정상이고 「이 데이터로 새 작업」 하나가 남는다 |

**결합과 재확인 면제는 다른 결정이다**(#932 B1). `_model_key_now()` 의 데이터 경로 결속은
조용한 게이트 우회의 재발 방지 조치이고, 강결합이 「데이터가 고정이니 재확인 불요」로 이어지면
그 방어가 녹는다. **함께 넘기지 않는다** — 결속이 서면 데이터가 안 갈리므로 그 키가 자연히
안정될 뿐이고, 갈리는 날에는 종전대로 강등된다.

**스키마 판정은 죽지 않는다.** `compatibility_for` 는 결속된 파일의 열이 사라진 경우를 잡는
실행 게이트·「확인 필요」 재진술로 계속 산다. 물러나는 것은 **후보 열거·순위**뿐이다.

#### 코드측 귀결

| 축 | 조치 |
|---|---|
| 링0 | `Job` 에 `data_path`·`data_sheet`·`data_header_row` 가산. `version` 은 올리지 않는다(구 JSON 이 기본값으로 「연결 필요」에 착지). 역인덱스 술어는 `data_binding_matches` 하나이고 경로 정규화는 판정 C 의 `excel_identity` 재사용 |
| 지문 | 결속은 `content_fingerprint` 에 **든다**(편집기가 덮어쓰는 값) — 제외 목록은 저장이 되싣거나 계산하는 메타 전용이다. `rules_values` 에는 **안 든다**: 결속은 실행 입력이지 규칙이 아니라, 넣으면 데이터를 바꿀 때마다 `binding_revision` 이 올라 겪지 않은 세대와 검토 요구가 선다 |
| 복제 | 결속을 **계승한다** — 복제의 뜻이 「같은 데이터로 하나 더」다. 미계승 목록(이력·즐겨찾기·검토 기준선·판본·권위)은 전부 실행·권위 **이력**이라 부류가 다르다 |
| 편집기 | 저장 착지와 저장본 진입이 결속을 재적재한다 — 저장 한 번이 데이터를 내려놓고 소스 어휘를 매핑 참조 키로 강등하던 자리가 그것이다. 「데이터 없이 진행」(`skip_data`)은 결속이 필수가 되며 죽었다 |
| 「문서 만들기」 | 작업 선택이 결속 데이터를 마운트하고, 후보는 결속 역인덱스가 된다. 데이터 전환의 KEEP/RELEASE 판정도 「이 데이터로 쓸 수 있나」에서 「이 데이터에 결속됐나」로 갈린다 |
| 노출 | 결속은 **템플릿 축과 같은 자리에서** 보인다 — 라이브러리 행이 「연결 필요」를 배지로, 상세가 정체(`data_label`)와 복구 동사를 낸다. 라벨 성형은 링0 `data_binding_label` 단일 출처라 표면이 basename·시트 표기를 짓지 않는다 |
| 실행 | 결속 없는 작업은 **생성이 막힌다**(`CONNECT_DATA` blocker · 게이트 단은 danger 뒤·세션 전제조건 앞). 저장 게이트만 요구하면 「필수」가 한 자리에서만 참인 말이 되기 때문이다. 좌초시키지는 않는다 — 복구 동사(`#jobConnectData` → 편집기)가 같은 화면에 함께 선다 |

**#880(U3 §6)과의 관계**: 앱 전역 「마지막 사용 데이터」 부팅 복원은 **한 칸짜리 완화**였지
결속이 아니었다. 그대로 산다 — 부팅은 마지막 데이터를 마운트하고, 화면은 그 데이터에 결속된
작업을 보인다. 설정 키 `last_data_source` 와 그 복원 경로는 불변이다.

**온보딩 커리큘럼이 이 뒤집기에 걸린다.** `docs/ONBOARDING_TUTORIAL.md` 의 L2(「한 마운트
위에서 작업만 갈아 끼워 여러 산출」)와 T12(데이터 교체)는 데이터-우선 세션을 가르치는데,
결속이 서면 데이터를 갈아 끼운다고 앞 작업이 그 데이터로 돌지 않는다 — 그것은 **연결을
바꾸는 일**이다. 실주행 대본은 그 동선(라이브러리 → 작업 편집 → 등록 데이터 → 재확정 →
변경 저장)을 이미 지나도록 이주했고, **커리큘럼 문안 자체의 재판정은 U4-F(튜토리얼
리서치)가 진다** — 이 라운드는 코드가 참인 것만 말하고 교재를 앞질러 고치지 않는다.

**동결 문서는 고치지 않는다**(#932 B1). 이 뒤집기는
`docs/archive/DATA_FIRST_INTEGRATION_MAP.md` 의 전제(방향 반전·세션 소유 데이터)를 무효화하지만
그 문서는 **왜 그런 표면이 됐는가**의 근거 원장이다. 승계 진술은 이 절과
`docs/UI_CONTRACT.md` 의 세션 계약 절이 진다.

### 2.5 「템플릿 변경사항」 존은 **조치가 있을 때만 선다** (12·24번)

뒤집는 판정: #932 **B5** 의 유보 — *"성립 경로는 둘이고 둘 다 새 결정이다"*. 사용자 확정
(2026-08-30)으로 경로 ⑴(확인 자동화)을 고르되, 조사 결과 그 경로의 재료가 **이미 저장소에
있었다**.

**12번이 그대로는 자기모순이었던 이유.** 이 존은 「변경이 있다」가 아니라 「확인할 수 있다」는
capability 존이고, 렌더 술어는 `has_job && supported` 뿐이라 **건수를 아예 묻지 않았다**.
물을 수가 없어서다 — 건수는 확인을 돌려야 나오고, 그 확인을 여는 단추가 존 안에 있다. 건수로
숨기면 확인을 개시할 방법이 사라진다.

**판정** 술어의 입력을 「확인 결과」가 아니라 **원본 드리프트**로 옮긴다.
`TemplateChangeCoordinator.source_drift_note` 가 캡처된 applied bytes 와 현재 원본 파일의
digest 를 이미 매 스냅샷 대조하고 있었고 `screen_job` 이 top-level `source_drift` 로 싣고
있었는데 — **웹 소비자가 0 건**이었다. 생산자만 살아 있고 화면에 안 붙은 상태다. 그래서 이
라운드가 한 일은 새 자동화를 짓는 것이 아니라 **이미 도는 값싼 신호를 노출 술어로 승격**하고
그 사실의 자리를 존 하나로 모은 것이다(top-level 사본은 걷었다 — 같은 사실의 두 자리).

세우는 갈래는 셋이다: `initialization_required` · 미종결 preparation · 드리프트
`changed`/`unknown`. 나머지 하나에서만 숨는다. **`unknown` 을 「없음」으로 접지 않는 것**이
U3 §3(#876) 단서(「미지정=조치 요구 상태는 숨기지 않는다」)를 넘지 않는 지점이다 — 종전
구현은 값싸게 못 구하면 `None`(=없음)으로 접었고, 그 위에 숨김을 세우면 읽지 못한 파일이
「변경 없음」으로 조용히 통과한다.

**24번이 같은 판정인 이유.** 「조치 필요」는 조치가 **없을 때도 늘 떠 있는** 구획에는 붙일 수
없는 이름이다. 술어가 서야 이름이 참이 되므로 12 를 안 하고 24 만 하면 그 문안이 거짓말이다.
적용 직후처럼 조치는 없는데 결과 재진술로 한 번 더 서는 자리에서는 옛 이름을 쓴다.

### 2.6 「변경사항 확인」의 **bootstrap 겸직**을 끊는다 (12번 파생 · 사용자 확정)

12번을 조사하다 드러난 별건이고 같은 변경에 담았다. lazy bootstrap 의 트리거는 「권위가
필요한 첫 동작」이었고 그건 확인(`check`)과 **생성**(`resolve_generation_template` — 주석에
"bootstrap-on-demand")이었다. 그런데 나중에 선 **「포함할 내용」(구간) 구획**이 세 번째
소비자가 되면서 자기 몫의 트리거를 못 받아 교착이 났다:

```
구간이 서려면 → 준비 필요 ;  생성이 열리려면 → 구간 필요 ;  준비를 자동으로 하는 것은 → 생성
```

유일한 탈출구가 **이름이 전혀 다른** 「변경사항 확인」 단추였고, 실주행 대본이 그 동선을
주석으로 해명하며 손으로 눌렀다(`scripts/live101/scenario.py`) — 대본이 해명해야 하는 동선은
대개 설계가 아니라 흉터다.

**옮기는 것은 bootstrap 이 아니라 「확인 한 바퀴」다**(실측). managed 실행 admission 이
capture·qualification·admission 의 산물을 요구하므로 bootstrap 만 옮기면 「'템플릿 변경사항
확인'을 먼저 실행하세요」라는 지시가 남는데, 그 지시가 겨누는 존은 방금 숨긴 그 존이다 —
#912 가 이름 붙인 결함류를 우리 손으로 만드는 꼴이다. 그리고 준비는 **착석 앞**이어야 한다:
뒤에 두면 vm 이 준비 전 사본을 들고 앉아, 생성 시점의 채택 대조가 그 간극을 「외부에서 바뀐
작업」으로 읽고 선택을 해제한다.

**판정** 준비는 **착석**(`job.select_job`)이 진다. `ensure_bootstrapped` 는 명령 경로에서만
불리고(렌더가 durable id 를 발급하는 write-on-read 금지는 그대로), 작업당 1회 단락하며, 같은
실물로 이미 실패한 기록이 있으면 되돌지 않는다. 거절은 삼키지 않는다 — 존이 비활성 + 진단으로
재진술한다. **자동 확인(seal)은 함께 켜지 않는다**: 종전 bootstrap 동사였던 「변경사항 확인」도
seal 을 켜지 않았으므로, 준비를 앞당긴 것이 seal 까지 딸려 켜면 그건 받지 않은 두 번째 변경이다.

두 곳(확인·생성)에 복제돼 있던 「좌석 + bootstrap + 좀비 권위 롤백(#804)」은 공유 입구
`_seat_bootstrapped_work` 하나로 모았다 — 갈리는 것은 `request_id` 하나뿐이다(확인은 재전송
키에서 파생해 멱등, 생성·자동 준비는 fresh id 로 재부트스트랩 가능성).

### 2.7 숨김이 연 창은 **두 층**이 닫는다 (12번 파생 · 사용자 확정)

존을 숨기면 앱 밖 편집(한글에서 템플릿 수정)이 push 를 내지 않아 다음 상호작용까지 침묵한다.
상시 노출이던 때는 단추가 늘 거기 있어 문제가 아니었다 — 숨김이 만든 새 창이다.

- **창 포커스 복귀**가 현재 화면을 다시 묻는다. 주기 검사(B5 가 비용으로 지목한 것)가 아니라
  사용자가 돌아온 순간 한 번이라 유휴 비용이 0 이다. 실패는 삼킨다 — 갱신은 편의이지 계약이
  아니고, 못 얻으면 다음 동작의 push 가 같은 값을 싣는다.
- **드리프트가 실행 게이트로 선다**(`REVIEW_TEMPLATE_CHANGE`). 생성은 캡처된 bytes 를 쓰므로
  (#681 F1) 막지 않으면 「검토한 편집분이 반영 안 된 문서」가 조용히 나온다. `unknown` 도 같이
  세운다 — 모르는 채 캡처본으로 미는 것이 곧 조용한 추측이다. 막되 좌초시키지 않는다:
  복구 동사(`#jobTplCheck`)는 **같은 판정이 세우는** 존 안에 있다.

두 층을 함께 두는 이유는 어느 하나도 충분하지 않아서다 — 포커스 갱신만 두면 놓친 창에서
조용히 틀리고, 게이트만 두면 「고쳐놓고도 모르는」 구간이 길다.

**생성이 최초 채택자인 경로는 죽지 않았다.** 준비가 거절된 뒤 템플릿을 수리하고 곧장 생성하는
자리가 그것이고, 그 경로의 계약(발급 순간의 사본 대조·push 규율·롤백)을 재던 테스트들은 단언을
지우지 않고 **도달 방법을 명시로 되만들어** 그대로 산다(`_unprepared_after_select`).

### 2.8 「포함할 내용」 구획은 **고를 항목이 있을 때만 선다** (13번)

적용 확장: U3 §3(#876)의 *"확인할 것이 없으면 숨김이 기본"*. #932 §4 가 13 을 12·24 와 갈라
남긴 이유는 **다른 구획**이라서였고, 그래서 그 구획의 「확인할 것」 정의를 먼저 세운다.

**사용자 확정(2026-08-30)** 구획은 **항목 ≥ 1** 일 때만 선다. 하위의 「보관된 선택」 구획은
**보관·손상 항목이 있거나 지금 저장할 선택이 있을 때** 선다.

**12번의 스위치 트랩이 왜 여기서 재현되지 않는가.** §2.5 가 12 를 뒤집어야 했던 이유는
「항목을 만드는 동사」가 그 구획 안에 있었다는 것이다(건수로 숨기면 개시할 방법이 사라진다).
「포함할 내용」에는 그 동사가 없다 — 구간을 세우는 것은 「변경사항 확인」(템플릿 존)이고 그
존은 §2.5 의 자기 술어로 따로 선다. 이 구획은 **이미 있는 항목을 고르는 자리**라 항목이 0 이면
개시할 것도 없다. 그래서 13 은 12 와 달리 술어의 입력을 옮길 필요가 없었다.

**프리셋은 그 트랩이 있었다.** 「현재 선택을 프리셋으로 저장」이 프리셋을 처음 만드는 **유일한
입구**라, 보관 0 건이라고 구획째 지우면 프리셋을 영영 만들 수 없다 — B5 가 템플릿 존에서
거절한 바로 그 모양이다. 그래서 술어의 입력이 목록 건수 하나가 아니다: 저장 동사의 게이트
(`has_declared_selection` — `PRESET_EMPTY_SELECTION` 을 세우는 그 함수)를 술어가 **함께**
묻는다. 보이는 단추가 곧 이행되는 단추이고, 아무것도 고르지 않은 갓 앉은 작업에서는 구획이
사라졌다가 사용자가 무언가 고르는 순간 돌아온다.

**판정의 자리는 셋이고 전부 Python 이다.**
`slot_configuration_projection.content_selection_zone_actionable`(구획) ·
`preset_command.preset_zone_actionable`(프리셋 구획) ·
`work_slot_configuration.has_declared_selection`(저장 게이트와 공유). 링2·웹은 그 값을 읽어
나르기만 한다 — 웹이 `slots.length` 를 다시 세면 같은 상태를 두 곳이 판정하게 되고, 그 둘 중
하나만 늙는다. 그 금지는 음성 단언이 진다(`tests/js/content_selection.test.js` — 항목이 있어도
backend 가 「세우지 않는다」고 실으면 웹은 그 말을 따른다).

**확정의 귀결을 명시로 남긴다.** 항목 0 건 ∧ 사라진 이전 선택 ≥ 1 인 상태에서 그 정보
(`cs-retained-gone`)는 **말할 자리를 잃는다**. detached·retained 축은 그대로 실려 나가고
표면만 서지 않는 것이라, 되살릴 때는 술어에 갈래 하나를 더하면 된다 — 조용히 갈린 것이
아님을 `tests/test_slot_configuration_projection.py` 의 명시 단언이 증언한다.

**두 개의 방어층.** ⑴ `CHOOSE_CONTENT` blocker 의 복구 동사가 이 구획 안 라디오
(`.cs-option-input`)라, 그 blocker 가 서는 두 상태(`NEEDS_SELECTION`·`HAS_BROKEN_SELECTIONS`)를
**술어의 입력에 명시 포함**한다. 오늘 두 상태는 항목 ≥ 1 을 함의하지만, 함의가 깨지는 날
조용히 사라지는 것이 하필 지시가 겨눈 자리다(#912 결함류). ⑵ 실패·거절·직전 왕복 결과의
재진술은 술어가 숨겨도 **살아남는다** — 재진술 수명은 웹 소유이고(#659) 술어만으로 지우면
사용자가 방금 겪은 거절이 화면에서 증발한다.

**숨김은 자리까지 걷는다.** React 술어는 children 을 비울 뿐이라 `.zone` 의 안쪽 여백과
`.zone + .zone` 구분선이 그대로 남아 **빈 상자**가 선다. `#jobContentSelectionZone:empty` 로
접고, 같은 결함을 이미 지고 있던 §2.5 의 `#jobTplChangeZone` 도 같은 규칙에 함께 실었다.

### 2.9 그리드 머리가 표를 다스린다 — #295 결정 1 폐기 (7·8·10·11번, U4-D1)

뒤집는 판정: **#295 결정 1** — *"1. 원본 순서 보존 — 역순정렬(최신 위) 제거. 그리드 순서 =
사용자 파일 순서 = 사용자 기억 순서"*. 그 이슈는 2026-07-31 갱신에서 이 항목을 **✅ 착지**로
적었으나 실코드의 기본값은 그때도 지금도 `VIEW_ORDER_DESC`(최신 행 먼저)다
(`screen_job.py` `VIEW_ORDER_*` · 새 세션과 `_reset_range_for_snapshot` 둘 다). 착지 판정이
낡았다(#932 B8 이 드리프트로 지목한 그 자리).

**판정** 기본값은 `sourceDesc` **유지**다(사용자 확정 2026-08-30). 7번의 요구는 기본값이 아니라
**컨트롤의 시각 비중**이었고, 그것은 `<select>` 를 표 머리 스위치로 바꾸는 것으로 해소된다.
#295 결정 1 은 여기서 명시 폐기하고, 그 잔여 스코프였던 2번(진입 시 최하단 스크롤)은 **전제가
사라진다** — 최신 행이 이미 맨 위다.

**8번은 근거 넷을 걷는다.** 「문서」 열의 이름·요약을 걷으면서 그 열을 근거로 들던 진술이
함께 죽는다: 표시순서에 확인 왕복을 두지 않는 근거(`UI_CONTRACT` F3) · 이름 충돌 꼬리표를
문안이 지지 않는 근거(`_order_note` docstring) · 미리보기 이름의 파생 설명 · 실패 행에서 표로
되찾는 동선. 같은 근거가 네 자리에 사본으로 있었다는 사실 자체가 이 정리의 소득이다. 확인
왕복은 **새로 두지 않는다** — 사용자 확정이 「그 이름은 왕복에 들어갈 가치도 없다」였다.
`row.name`·`row.summary` payload 는 살아 있다(필터 밖 선택 칩이 소비한다 — 생산자 0 아님).

**10·11번은 자리를 옮길 뿐 의미를 바꾸지 않는다.** 「펼쳐서 행 고르기」는 진입점만 표 머리로
오고 초안 거래(§18.11-21)는 그대로다. 「전체 선택/해제」는 체크박스 열 머리의 3상태로 접히되
**id 를 유지한다** — 자리는 바뀌어도 동사가 같아서 `SELECT_RECORDS` 복구 동사 선언과 실주행
대본이 그대로 산다. 3상태는 **보이는 행** 기준이다(백엔드가 필터 활성 시 매치만 가산하므로
전체 레코드로 재면 필터를 켠 채 다 골라도 영영 「일부」다).

**옮긴 트리거의 초점 계약.** 「펼쳐서 행 고르기」가 표 머리로 오면서 **면과 함께 언마운트되는
표면 안**으로 들어왔다 — 오버레이가 저장해 둔 복귀 노드가 닫힘 시점에 이미 죽어 있다. 그래서
닫힘 뒤 살아 있는 같은 단추로 초점을 다시 건다. 「누른 자리로 돌아온다」는 계약은 그 자리가
옮겨졌다고 없어지지 않는다.

### 2.10 프리셋을 위로, 끝난 슬롯은 접는다 (14~17번, U4-D2)

**원문이 없다.** 34항 중 14~17 은 #932 §1 이 「항목·선택·프리셋 노출 루프(프리셋 우선·조건부
접힘)」 한 줄로 접어 둔 것이 유일한 기록이고, 저장소·이슈 어디에도 항목별 문장이 없다(탐색으로
확인). 그래서 **사용자 확정(2026-08-30)이 원문을 대신하는 정본**이다: 프리셋을 슬롯 위로 올리고
끝난 슬롯은 접는다. 다음 사람이 네 항목을 다시 찾아 헤매지 않도록 여기 적어 둔다.

**요구의 실체는 길이다.** 슬롯이 늘수록 다 고른 항목의 라디오가 자리를 먹어, 한 번에 끝내는
길(프리셋)이 화면 밖으로 밀린다. 그래서 두 조치가 한 판정이다 — 먼저 보여 주기와 짧게 만들기.

**접힘 술어는 Python 한 곳**(`slot_settled`)이고 링2·웹은 읽어 나른다. 접지 **않는** 갈래를
술어가 먼저 못박는다: blocking 상태 · `RESOLVED` 아님 · 진단이 남음 · 이전 선택의 운명 문안이
붙음 · 실효 선택 없음. 마지막 갈래의 이유는 접은 줄이 **고른 값을 대신 말하기** 때문이다 —
댈 값이 없으면 「접혔다」와 「비었다」가 같아 보인다.

**26번을 되돌리지 않는 것이 이 판정의 안전장치다.** U4-A 26번은 「옵션을 고르면 구획이 접혔다
깜빡인다」를 고쳤다. 접힘을 매 왕복마다 다시 계산하면 사용자가 라디오를 고른 순간 그 슬롯이
`RESOLVED` 가 되어 **눈앞에서 접힌다** — 같은 결함을 우리 손으로 되만드는 꼴이다. 그래서 접힘은
초기 상태로만 적용하고, **이 세션에서 만진 슬롯은 접지 않는다**. 그 기억은 표시 상태라 웹이
소유하고 영속하지 않으며, 구성이 갈리면(slot 집합이 바뀌면) 버린다. 상태가 걸린 사실이라 정적
렌더 테스트가 못 보고 **실주행이 진다**.

**접힌 슬롯도 DOM 에 남는다.** `cs-opt-N-M` 은 렌더 순서 기반 id 이고 실주행 대본이 그 좌표를
든다 — 걸러내면 뒤 슬롯의 index 가 전부 밀려 대본이 **다른 슬롯을 누르고도 초록**일 수 있다
(조용한 오탐). `<details>` 의 네이티브 접힘은 자식을 남기므로 index 가 불변이고 키보드 조작도
공짜로 얻는다. 다만 닫힌 `<details>` 안의 요소도 `el.click()` 은 통과하므로, 대본은 **펼치는
걸음**을 명시로 밟는다(`_pick_option`) — 사람이 밟는 경로와 대본이 밟는 경로를 같게 둔다.

**`CHOOSE_CONTENT` 가 겨누는 자리는 접히지 않는다.** 그 blocker 의 복구 동사가 슬롯 안의
라디오라, 접으면 「없는 자리를 가리키는 지시」가 된다(#912 결함류). `RESOLVED` 판정이 이미 그
상태들을 배제하지만 **결과가 아니라 술어의 입력**으로 적었다 — 13번이 구획 술어에 같은 이유로
같은 장치를 둔 것과 같다.

**프리셋 구획은 둘로 갈렸다.** 통째로 올리면 저장 동사도 위로 가 「지금 고른 것을 보관한다」가
고르는 자리보다 **앞에** 서서 인과가 뒤집힌다. 그래서 목록(적용)은 슬롯 위, 저장은 슬롯 아래이고
술어도 각자다 — `preset_list_actionable`(보관·손상)과 저장 게이트 그 자체
(`has_declared_selection`). 13번의 3항 OR 은 두 구획의 술어를 합집합으로 뭉쳐 놓은 것이었고,
술어가 늘지 않고 **정확해졌다**(합집합 동치는 테스트가 옛 식을 직접 써서 증언한다 — 죽은 함수를
프로덕션에 남기지 않기 위해서다).

### 3.1 태그·그룹은 걷되 **동결**한다 (30번)

사용자 확정(2026-08-29): 「표면 제거, 내부 코드는 봉인 상태로 나중에 재활용하도록 동결」.
나라장터 소스와 같은 처분이고 CLAUDE.md 작업 규율에 같은 꼴로 등재했다.

**걷은 것(표면)** — 작업 그룹(지정·개명·해산·접힘)과 템플릿 그룹(같은 넷) 동사 10종,
태그 편집기와 상세의 태그 필, **태그 facet 칩**(`toggle_facet`·`clear_facets`), 그룹 이동
다이얼로그 둘(`libraryMoveModal`·`tplMoveModal` — `group_move_dialog.ts` 는 파일째 삭제),
라이브러리 구획 헤더와 편집기 밴드의 구획 헤더.

facet 을 함께 걷은 이유는 결속이다: 태그의 **유일한 소비처**가 그 칩이라, 편집기만 걷으면
「만들 수도 고칠 수도 없는 데이터로 좁히는 칩」이 남는다 — 신규 사용자에게는 영영 빈 줄이다.

**남긴 것(동결)** — `Job.tags`·`Job.group` durable 필드와 그 직렬화, `application/jobs` 의
group 함수들, `webapp/template_groups.py`(모델·영속·`reconcile`), 설정 키
`template_groups`·`job_collapsed_groups`, 링1 `HomeViewModel` 의 group·facet 판정. 전부
자기 테스트가 계속 진다. 링2 는 그 축을 **묻지 않는다**: `library_sections(grouped=False)` ·
`build_sections(grouped_view=False)` 두 갈래가 「저장된 지정이 남아 있어도 구획을 만들지
않는다」를 한 자리에서 말한다 — 지울 동사가 없는 헤더를 그리면 그것이 곧 #912 가 이름 붙인
「복구 동사 없는 표면」이다.

**부수 판정 둘.** ⑴ 예제팩은 설치 때 그룹 지정을 **계속 한다**(동결 상태를 일관되게 두면
되살릴 때 예제가 묶인 채 돌아온다). 대신 설치·제거 확인 문안에서 그룹 줄을 뺐다 — 보이지 않는
소속을 약속하면 그 문안이 거짓이다. live101 의 T0 그룹 게이트는 **음성 단언**으로 뒤집었다
(걷힌 어휘가 화면에 되살아나면 실패). ⑵ 「문서 만들기」 dispatch 의 `needs_confirm` 무-push
갈래는 마지막 생산자가 그룹 병합·해산 승격이라 **생산자 0** 이 됐다 — 도달 불가 분기를 남기지
않고 걷었다(확인 왕복을 되들이는 핸들러가 생기면 자기 테스트와 함께 돌아온다).
